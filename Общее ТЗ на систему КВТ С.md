## 1. Общие сведения

### 1.1 Назначение системы

Комплект измерения температуры и влажности "КВТ" предназначен для автоматического измерения температуры и влажности датчиками С2000-ВТ / С2000-ВТИ (Болид) и дальнейшей обработки, хранения с привязкой по времени и визуализации.

Комплект рассчитан на работу с **одним или несколькими преобразователями интерфейсов С2000-ПП** (Болид), которые обеспечивают связь между шинами RS-485 (протокол «Орион») и Modbus RTU. Каждый С2000-ПП подключается к отдельной именованной линии опроса: COM-порту или UDP-каналу с RTU-кадром внутри транспортной обёртки.

**Ссылки:**
- Датчик С2000-ВТ: https://bolid.ru/production/s2000-vt.html
- Датчик С2000-ВТИ: https://bolid.ru/production/s2000-vti.html
- Преобразователь С2000-ПП: https://bolid.ru/production/s2000-pp.html

### 1.2 Масштабируемость системы

Система поддерживает до **256 датчиков** С2000-ВТ / С2000-ВТИ на одном С2000-ПП:

- Датчики можно добавлять по одному или группами
- Датчики можно удалять в любой момент
- Максимальное количество датчиков: **256** (ограничение адресного пространства С2000-ПП)
- Каждый датчик занимает 2 адреса Modbus (температура + влажность), итого до 512 адресов
- Рекомендуемые конфигурации для типовых решений:

| Конфигурация | Количество датчиков | Адреса Modbus |
|--------------|---------------------|---------------|
| КВТ-10 | до 10 | 20 адресов |
| КВТ-20 | до 20 | 40 адресов |
| КВТ-40 | до 40 | 80 адресов |
| КВТ-60 | до 60 | 120 адресов |
| КВТ-256 | до 256 | 512 адресов |
| Произвольная | N датчиков (≤256) | 2×N адресов |

### 1.3 Целевая платформа

- **Основная:** ARM v7 4-ядерный контроллер
- **Совместимость:** Linux x86_64, Windows (ПК, серверы)
- **Контейнеризация:** Docker

## 3. Подсистема 1: Modbus Poller

### 3.1 Функциональные требования

- Опрос регистров функцией 0x04 (Read Input Registers)
- **Адреса регистров значений:** 30000 + N (Input Registers)
- **Адреса регистров статусов:** 40000 + N (Holding Registers)
- Чётный адрес - температура, нечётный - влажность
- Непрерывный опрос без остановки
- Логирование обмена по Modbus
- Настройка одной или нескольких линий опроса
- Поддержка линий типа `serial`, `udp_rtu` и `udp_c2000pp`
- Привязка каждого датчика к конкретной линии опроса через уникальное имя порта
- Сохранение в текущих данных и журнале не только Modbus-адреса, но и источника опроса

### 3.2 Параметры подключения (настраиваемые)

Параметры делятся на общие параметры цикла и параметры отдельных линий опроса.

| Параметр | По умолчанию | Диапазон |
|----------|--------------|----------|
| Период опроса | 1000 мс | 100-60000 мс |
| Таймаут | 500 мс | 100-10000 мс |
| Количество повторов | 3 | 0-10 |
| Базовый адрес значений | 30000 | 0-65535 |
| Базовый адрес статусов | 40000 | 0-65535 |
| Максимум записей Modbus-лога | 1000 | 1-50000 |

Каждая линия опроса имеет обязательный `id`, человекочитаемое уникальное `name`, тип транспорта и собственные параметры подключения. `name` используется в интерфейсе и в нумерации датчиков, поэтому должен быть стабильным: например `COM8`, `PP-SKLAD-UDP`, `UDP-192.168.66.100`.

| Тип линии | Назначение | Обязательные поля |
|-----------|------------|-------------------|
| `serial` | Опрос С2000-ПП через COM-порт как Modbus RTU | `com_port`, `baudrate`, `bytesize`, `parity`, `stopbits` |
| `udp_rtu` | Нативный RTU-over-UDP: UDP-датаграмма содержит чистый Modbus RTU кадр с CRC16 | `remote_host`, `remote_port`, опционально `local_host`, `local_port` |
| `udp_c2000pp` | RTU-over-UDP через 5-байтовую обёртку преобразователя | `remote_host`, `remote_port`, `local_host`, `local_port`, `seq_start`, `prefix`, `channel` |

### 3.2.1 UDP-обёртка С2000-ПП

Для транспорта `udp_c2000pp` каждый готовый Modbus RTU кадр, включая CRC16, перед отправкой заворачивается в один UDP-датаграмм с 5-байтовым заголовком:

```
 +------+------+--------+------+===============================+
 | 0x10 | LEN  |  SEQ   | 0x10 |   Modbus RTU frame (LEN байт) |
 +------+------+--------+------+===============================+
 байт0  байт1  байт2-3  байт4   байт5 ... байт(5+LEN-1)
```

| Поле | Размер | Значение | Назначение |
|------|--------|----------|------------|
| `prefix` | 1 байт | всегда `0x10` | Маркер начала пакета |
| `LEN` | 1 байт | длина вложенного RTU-кадра | Количество байт после заголовка |
| `SEQ` | 2 байта, big-endian | счётчик пакетов, например `0x21D1`, `0x21D2`, ... | Информационный номер пакета стороны-отправителя |
| `channel` | 1 байт | всегда `0x10` | Канал/адрес преобразователя |
| `payload` | `LEN` байт | Modbus RTU кадр + CRC16 | Полезная нагрузка |

Правила обмена:

- отправка: верхний слой формирует обычный Modbus RTU кадр с CRC16, транспортный слой добавляет заголовок `prefix/LEN/SEQ/channel` и отправляет обёрнутую UDP-датаграмму на `remote_host:remote_port`;
- приём: транспортный слой принимает следующую UDP-датаграмму в той же обёртке `prefix/LEN/SEQ/channel`, проверяет заголовок, логирует приборный `SEQ`, проверяет `LEN`, снимает 5 байт заголовка и только после этого отдаёт чистый Modbus RTU кадр верхнему разбору;
- чистый RTU-ответ без 5-байтовой обёртки для транспорта `udp_c2000pp` считается ошибкой протокола и логируется как `invalid_udp_wrapper`;
- локальный порт: для штатной схемы ПК `192.168.66.97:40005` и прибор `192.168.66.100:40005`, поэтому UDP-сокет должен уметь bind на заданные `local_host` и `local_port`;
- TX SEQ: хранится отдельно на каждую UDP-линию, увеличивается на 1 на каждый запрос, при переполнении переходит по модулю `0x10000`;
- RX SEQ: не является эхом запроса; С2000-ПП/преобразователь ведёт собственный независимый счётчик ответных датаграмм, поэтому RX SEQ только логируется и не сравнивается с TX SEQ;
- сопоставление ответа: канал используется как синхронный COM-порт поверх UDP, ровно один запрос -> один следующий ответ; перед отправкой нового запроса socket очищает протухшие UDP-датаграммы, а корреляция выполняется по вложенному Modbus RTU кадру: slave id, function/function|0x80, длина и CRC16;
- проверка заголовка: `prefix` и `channel` в принятой обёртке должны соответствовать настройкам линии, по умолчанию `0x10` и `0x10`;
- LEN: в ответе проверяется отдельно и должен совпадать с длиной вложенного RTU-кадра;
- распаковка: после проверки заголовка верхнему Modbus-разбору передаётся только чистый RTU-кадр;
- CRC16: обёртка не меняет и не заменяет Modbus CRC16; после распаковки CRC проверяется тем же кодом, что и для COM-порта;
- таймаут: если до истечения `timeout_ms` не пришла следующая валидная обёрнутая датаграмма с корректным Modbus RTU кадром, запрос считается неуспешным и проходит обычную логику повторов.

### 3.2.2 Многоканальный опрос

Опросчик должен обслуживать несколько линий опроса в одном процессе через менеджер портов. Опрос каждой линии `serial`, `udp_rtu` или `udp_c2000pp` должен выполняться независимо: отдельный worker, отдельное транспортное состояние, отдельная статистика и отдельный жизненный цикл подключения. Последовательный общий цикл по всем портам не допускается как финальная реализация, потому что таймаут одного С2000-ПП не должен задерживать остальные COM/UDP-линии.

#### 3.2.2.1 Менеджер портов опроса

`PollPortManager` является центральным компонентом Modbus Poller и управляет всеми линиями опроса.

Обязанности менеджера:

- загрузить и провалидировать список `poll_ports[]`;
- создать worker на каждую включённую линию;
- передать каждому worker только датчики его `poll_port_id`;
- запускать, останавливать и перезапускать отдельную линию без остановки остальных;
- хранить реестр состояний портов: `configured`, `starting`, `running`, `degraded`, `error`, `stopped`, `disabled`;
- агрегировать `current.json` из последних снимков всех workers;
- агрегировать `modbus_log.json`, сохраняя в каждой записи `poll_port_id`, `poll_port_name` и transport metadata;
- принимать изменения конфигурации из API и UI, вычислять diff и перезапускать только затронутые линии;
- не допускать удаления линии, к которой привязаны датчики;
- отдавать одинаковую модель данных в Modbus Poller UI и в Visualizer `/settings/poller`.

Worker линии:

- владеет одним COM handle или одним UDP socket;
- для `udp_c2000pp` владеет своим TX-счётчиком SEQ, логирует независимый RX-счётчик прибора и очищает протухшие UDP-датаграммы перед новым запросом;
- выполняет цикл опроса только своих датчиков;
- помечает offline только свои датчики;
- пишет собственные ошибки в состояние порта, не меняя состояние остальных портов;
- поддерживает остановку и reconnect между циклами без потери состояния других линий.

Требования:

- датчики группируются по `poll_port_id`;
- на каждую активную линию создаётся отдельный Modbus-клиент и отдельное транспортное состояние;
- для COM-линий открывается отдельный serial handle;
- для UDP-линий создаётся отдельный UDP socket с собственным `local_host/local_port`;
- статистика ведётся глобально и по каждой линии: `total_polls`, `successful_polls`, `failed_polls`, `timeouts`, `crc_errors`, `last_error`, `last_poll_at`, `last_success_at`;
- перезагрузка конфигурации не должна ронять весь сервис: изменённая линия переподключается между циклами, остальные продолжают работать;
- если линия недоступна, offline получают только датчики этой линии.

### 3.2.3 Нумерация и уникальность датчиков

Глобальный `sensor.id` остаётся внутренним неизменяемым идентификатором для архива, ссылок и API. В пользовательском интерфейсе дополнительно отображается номер датчика внутри линии опроса:

```
<poll_port.name>-<sensor.local_number>
```

Примеры: `COM8-001`, `COM8-002`, `UDP-192.168.66.100-001`, `PP-SKLAD-UDP-014`.

Правила:

- `poll_port.name` должен быть уникальным среди всех линий;
- `local_number` уникален только внутри своей линии;
- пара `(poll_port_id, modbus_slave_id, modbus_addr_temp, modbus_addr_hum)` должна быть уникальной;
- одинаковые Modbus-адреса допустимы на разных линиях;
- при миграции старой конфигурации всем существующим датчикам назначается линия `default`, а `local_number` вычисляется по текущему порядку датчиков.

### 3.3 Структура датчика С2000-ВТ

Один датчик С2000-ВТ занимает 2 адреса Modbus:

**Регистры значений (30000 + N):**
- **Адрес N (чётный):** Температура (°C × 10, знаковое 16-бит)
- **Адрес N+1 (нечётный):** Влажность (% × 10, беззнаковое 16-бит)

**Регистры статусов (40000 + N):**
- **Адрес N (чётный):** Статус канала температуры
- **Адрес N+1 (нечётный):** Статус канала влажности

| Статус | Описание |

| warning_high_temp | Превышение верхней границы температуры |

| warning_high_hum | Превышение верхней границы влажности |
| warning_low_hum | Принижение нижней границы влажности |
| alarm | Критическое отклонение (более X% от границы) |
| no_connection | Нет связи с датчиком |
| guarded | На охране (мониторинг границ активен) |

> Visualizer должен проксировать эти же операции в `/settings/poller`: список линий, состояние manager/workers, старт/стоп/перезапуск одной линии, сохранение линии, удаление свободной линии, scan по выбранной линии и просмотр логов по линии.

## 4. Подсистема 2: Archive Manager

### 4.1 Функциональные требования

- Копирование данных из current.json в архив (по таймеру или по изменению)
- Поддержка нескольких хранилищ: SQLite, PostgreSQL, JSON-файл
- Компрессия данных (схлопывание одинаковых значений)
- Управление размером архива
- Резервирование свободного места на диске
- Автоматическая ротация старых данных

### 4.2 Режимы забора данных

Система архивирования поддерживает два режима забора данных из опросчика Modbus:

#### 4.2.1 Режим по таймеру (periodic)

Архиватор периодически читает файл `current.json` с заданным интервалом.

| Параметр | По умолчанию | Диапазон |
|----------|--------------|----------|
| archive_period_ms | 1000 | 100-60000 мс |

**Особенности:**
- Простая реализация
- Предсказуемая нагрузка на систему
- Возможна потеря данных при периоде архивации > периода опроса

#### 4.2.2 Режим по изменению файла (watch)

Архиватор отслеживает изменения файла `current.json` и забирает данные сразу после обновления.

**Особенности:**
- Гарантированный захват всех данных
- Минимальная задержка архивации
- Нагрузка зависит от частоты опроса

#### 4.2.3 Комбинированный режим (combined)

Сочетает оба подхода: отслеживает изменения файла, но не чаще заданного интервала.

| Параметр | По умолчанию | Описание |
|----------|--------------|----------|
| min_interval_ms | 500 | Минимальный интервал между архивациями |
| max_interval_ms | 5000 | Максимальный интервал (принудительное чтение) |

#### 4.2.4 Конфигурация режимов забора данных

```json
{
  "data_collection": {
    "mode": "combined",
    "source_file": "./data/current.json",
    "periodic": {
      "enabled": false,
      "interval_ms": 1000
    },
    "watch": {
      "enabled": true,
      "debounce_ms": 100
    },
    "combined": {
      "enabled": true,
      "min_interval_ms": 500,
      "max_interval_ms": 5000
    }
  }
}
```

#### 4.2.5 Диаграмма режимов

```mermaid
flowchart LR
    subgraph periodic [Режим periodic]
        T1[Таймер] -->|каждые N мс| R1[Чтение файла]
    end
    
    subgraph watch [Режим watch]
        F1[Изменение файла] -->|событие| R2[Чтение файла]
    end
    
    subgraph combined [Режим combined]
        F2[Изменение файла] -->|событие| D[Debounce]

    end
```

### 4.4 Алгоритм компрессии данных

Для экономии места одинаковые последовательные значения "схлопываются":

```
Исходные данные (каждую секунду):
  15:00:00 - 23.5°C
  15:00:01 - 23.5°C
  15:00:02 - 23.5°C
  15:00:03 - 23.6°C
  15:00:04 - 23.6°C

Сжатые данные:
  15:00:00 - 23.5°C (duration: 3s, count: 3)
  15:00:03 - 23.6°C (duration: 2s, count: 2)
```

### 4.5 Схема БД SQLite/PostgreSQL

```sql
-- Таблица датчиков
CREATE TABLE sensors (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    modbus_slave_id INTEGER,
    modbus_addr_temp INTEGER,
    modbus_addr_hum INTEGER,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Таблица измерений (со схлопыванием)
CREATE TABLE measurements (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sensor_id INTEGER REFERENCES sensors(id),
    timestamp_start TIMESTAMP NOT NULL,
    timestamp_end TIMESTAMP NOT NULL,
    duration_seconds INTEGER,
    sample_count INTEGER DEFAULT 1,
    temperature REAL,
    humidity REAL,
    temp_status TEXT,
    hum_status TEXT,
    combined_status TEXT
);

-- Индекс для быстрого поиска
CREATE INDEX idx_sensor_time ON measurements(sensor_id, timestamp_start);

-- Таблица событий (тревоги, квитирование)
CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sensor_id INTEGER REFERENCES sensors(id),
    timestamp TIMESTAMP NOT NULL,
    event_type TEXT NOT NULL,
    value REAL,
    threshold REAL,
    acknowledged BOOLEAN DEFAULT FALSE,
    acknowledged_at TIMESTAMP,
    acknowledged_by TEXT,
    comment TEXT
);

-- Журнал температур и влажности (агрегированные данные по периодам)
CREATE TABLE temperature_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sensor_id INTEGER REFERENCES sensors(id),
    period_type TEXT NOT NULL,          -- 'hour', 'day', 'week'
    period_start TIMESTAMP NOT NULL,
    period_end TIMESTAMP NOT NULL,
    temp_min REAL,
    temp_max REAL,
    temp_avg REAL,
    hum_min REAL,
    hum_max REAL,
    hum_avg REAL,
    sample_count INTEGER DEFAULT 0
);

CREATE INDEX idx_temp_log_sensor_period ON temperature_log(sensor_id, period_type, period_start);

-- Журнал превышений (фиксация каждого выхода за границы)
CREATE TABLE threshold_violations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sensor_id INTEGER REFERENCES sensors(id),
    started_at TIMESTAMP NOT NULL,
    ended_at TIMESTAMP,
    duration_seconds INTEGER,
    parameter TEXT NOT NULL,            -- 'temperature', 'humidity'
    violation_type TEXT NOT NULL,       -- 'warning_high', 'warning_low', 'alarm_high', 'alarm_low'
    value_at_start REAL,
    value_peak REAL,
    threshold REAL,
    acknowledged BOOLEAN DEFAULT FALSE,
    acknowledged_at TIMESTAMP,
    acknowledged_by TEXT,
    comment TEXT
);

CREATE INDEX idx_violations_sensor ON threshold_violations(sensor_id, started_at);
CREATE INDEX idx_violations_open ON threshold_violations(ended_at) WHERE ended_at IS NULL;

-- Таблица статистики архива
CREATE TABLE archive_stats (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    total_records INTEGER,
    disk_usage_bytes INTEGER,
    compression_ratio REAL
);
```

## 5. Подсистема 3: Web Visualizer

### 5.1 Функциональные требования

#### 5.1.1 Главный экран (мнемосхема)

- Отображение произвольного количества плашек датчиков
- Загрузка фоновой подложки (изображение)
- Перетаскивание плашек (drag & drop)
- Изменение размера плашек
- Сохранение расположения
- Группировка плашек по пользовательским группам
- Редактор групп: создание, переименование, удаление, выбор цвета/сворачивания, перенос датчиков между группами
- Фильтрация и сортировка плашек по линии опроса (`poll_port_id`/`poll_port_name`), группе, статусу и имени
- Отдельная плашка доступности по линии («Доступность Ethernet-линий») на мнемосхеме НЕ выводится. Доступность/ping показываются в карточке каждого датчика, привязанного к Ethernet-линии (см. 5.1.2)
- Дерево датчиков с режимом редактирования (см. 5.1.9)

#### 5.1.2 Плашка датчика

- Видимый номер датчика в формате `<имя линии>-<номер внутри линии>`
- Название датчика (задаётся в настройках)
- Текущая температура (число + индикатор)
- Текущая влажность (число + индикатор)
- Статус (цветовая индикация)
- Адреса Modbus
- Имя линии опроса и тип транспорта: COM, UDP RTU или UDP С2000-ПП
- Мини-график за последний час
- Метка актуальности данных каждой плашки: "Последние данные: <дата/время>"
- Источник времени: `temperature.timestamp` датчика (fallback: общий `current.timestamp`)
- «Получено данных сегодня» — счётчик успешных снимков датчика за сутки (из `availability_daily.json`)
- «Ping линии» — строка выводится ТОЛЬКО для датчиков, привязанных к Ethernet-линии (`udp`/`udp_rtu`/`udp_c2000pp`); показывает последний результат ping линии опроса данного датчика (`<мс> мс`, `нет связи` или `—`). Значение берётся по `poll_port_id` датчика из суточного учёта доступности линий. Для датчиков на COM-линии строка ping скрыта

#### 5.1.3 Детальный просмотр датчика

- График температуры/влажности
- Масштабирование: час/день/неделя/месяц/год
- Журнал событий датчика
- Настройки границ
- Кнопка квитирования

#### 5.1.4 Настройки системы

- Конфигурация опросчика Modbus
- Редактор линий опроса: список линий, добавление COM/UDP, включение/выключение, проверка связи, удаление неиспользуемых линий
- Настройка UDP С2000-ПП: локальный IP/порт, удалённый IP/порт, стартовый SEQ, просмотр последнего SEQ, prefix/channel только как расширенная настройка
- Страница `/settings/poller` в Visualizer должна иметь тот же функциональный объём, что и сервисная страница Modbus Poller: таблица линий, состояние `PollPortManager`, состояние каждого worker, старт/стоп/перезапуск отдельной линии, scan по выбранной линии, последние обмены и ошибки по выбранной линии
- Все изменения линий из `/settings/poller` должны идти через API Modbus Poller или через visualizer-proxy к тем же endpoint, чтобы не появлялись два разных источника правды
- Настройка каждого датчика (добавление, удаление, редактирование)
- Привязка каждого датчика к линии опроса и назначение номера внутри линии
- Настройка архивирования
- Настройка уведомлений

#### 5.1.9 Дерево датчиков (на мнемосхеме)

- Отдельный блок «Дерево датчиков» на главном экране (мнемосхеме) для логической группировки датчиков по веткам
- Дерево независимо от группировки плашек и от планов помещений; хранится в отдельном файле `mnemo_tree.json`
- Поддержка вложенных веток (подветок); ограничение глубины вложенности — 8 уровней
- Каждая ветка содержит: название, список привязанных датчиков (`sensor_ids`) и список подветок (`children`)
- Один датчик может входить в несколько веток
- В корне каждой ветки отображаются:
  - название ветки;
  - количество датчиков в ветке (с учётом всех подветок);
  - текущий диапазон минимум-максимум температуры по датчикам ветки;
  - текущий диапазон минимум-максимум влажности по датчикам ветки.
- Диапазоны min/max вычисляются по текущим значениям датчиков и обновляются в реальном времени вместе с показаниями
- Ветки сворачиваются/разворачиваются; состояние сворачивания сохраняется между авто-обновлениями страницы
- Листья ветки (датчики) повторяют данные плашки датчика: имя, текущие температуру и влажность, название линии опроса, время последних данных, число полученных данных за сегодня и ping линии (для Ethernet-линий); являются ссылкой на детальный просмотр датчика
- Режим редактирования мнемосхемы: кнопка «Режим редактирования» в шапке главного экрана включает встроенный (inline) редактор дерева под деревом. В режиме редактирования доступны: добавление веток и подветок, переименование, удаление, выбор датчиков в ветку чекбоксами, сохранение и отмена изменений
- Флаг «Показывать плашки вне дерева (все плашки)» в режиме редактирования: управляет отображением общей сетки плашек датчиков. Если выключен — сетка скрывается и на мнемосхеме остаётся только дерево. Изменение применяется сразу (живой предпросмотр) и сохраняется в `mnemo_tree.json` (поле `show_flat_cards`, по умолчанию `true`)
- При сохранении выполняется санация: пустые/повторяющиеся идентификаторы веток переназначаются, дубликаты и некорректные `sensor_ids` отбрасываются

```json
      "last_network_available": true,
      "last_ping_ms": 3.0,
      "network_history": [
        { "timestamp": "2026-06-17T12:22:42", "available": true, "ping_ms": 3.0 }
      ]
    }
  }
}
```

| Поле | Описание |
|------|----------|
| sensors[].received_today | Количество успешных снимков датчика за сутки (значение «Получено данных сегодня») |
| sensors[].availability_percent | Доля успешных снимков от общего числа за сутки |
| ports[].network_availability_percent | Процент успешных сетевых проверок (ping) линии за сутки |
| ports[].last_ping_ms | Последний измеренный ping линии, мс (для значения «Ping линии» в карточке датчика) |
| ports[].network_history | История точек доступности линии (доступна через API, на мнемосхеме отдельной плашкой не отображается) |

> Ping выполняется только для Ethernet-линий (`udp`/`udp_rtu`/`udp_c2000pp`). Для COM-линий сетевая проверка не производится, и строка «Ping линии» в карточке датчика скрывается.

### 5.9 Формат конфигурации дерева датчиков (mnemo_tree.json)

```json
{
  "branches": [
    {
      "id": "br1",
      "name": "Этаж 1",
      "sensor_ids": [1, 2, 3],
      "children": [
        {
          "id": "br2",
          "name": "Серверная",
          "sensor_ids": [4],
          "children": []
        }
      ]
    }
  ],
  "show_flat_cards": true,
  "updated_at": "2026-06-17T12:28:02"

```

| Поле | Описание |
|------|----------|
| branches[].id | Идентификатор ветки (генерируется/нормализуется на сервере: `br1`, `br2`, …) |
| branches[].name | Название ветки (до 80 символов) |
| branches[].sensor_ids | ID датчиков из `system_config.json`, привязанных к ветке (дубликаты отбрасываются) |
| branches[].children | Вложенные подветки (та же структура, глубина до 8 уровней) |
| show_flat_cards | Показывать ли общую сетку плашек вне дерева (`true` по умолчанию); `false` — на мнемосхеме остаётся только дерево |

### 6.4 Формат регулярного отчёта

Отчёт включает:

1. Сводную таблицу по всем датчикам (текущие значения, статусы)
2. Диапазоны температур/влажности за период (min / max / avg)
3. Количество и длительность превышений за период
4. Графики температуры и влажности (изображения)

Пример текстовой части:

```

  Влажность: 35.2 .. 62.1% (avg 48.7%)
  Превышений: 0

```

### 6.5 Генерация графиков

Бот генерирует графики с помощью matplotlib:

- Линейный график температуры и влажности за период
- Отображение границ (warning/alarm) горизонтальными линиями
- Подсветка зон превышений
- Поддержка периодов: 1 час, 6 часов, 24 часа, 7 дней, 30 дней
- Формат вывода: PNG изображение

### 6.6 Планировщик отчётов

Планировщик на базе APScheduler поддерживает:

### 7.5 Валидация конфигурации

При изменении конфигурации выполняется валидация:

| Проверка | Описание |
|----------|----------|
| Уникальность ID | ID датчика должен быть уникальным |
| Уникальность адресов | Адреса Modbus не должны пересекаться внутри одной линии опроса; одинаковые адреса на разных `poll_port_id` допустимы |
| Привязка к линии | `poll_port_id` должен ссылаться на существующую включённую или отключённую линию опроса |
| Номер внутри линии | `local_number` должен быть уникальным в пределах одного `poll_port_id` |
| Границы значений | min < max для всех лимитов |
| Обязательные поля | name, modbus_slave_id, адреса |
| Допустимые значения | slave_id: 1-247, адреса: 0-65535 |

### 7.6 Миграция конфигурации

При изменении схемы конфигурации (config_schema_version) система автоматически мигрирует старые конфигурации:

```python
# Пример миграции с версии 0.9 на 1.0
def migrate_0_9_to_1_0(old_config):
    new_config = old_config.copy()
    new_config["config_schema_version"] = "1.0"
    
    # Добавляем новые обязательные поля
    for sensor in new_config["sensors"]:
        if "warning_delta" not in sensor["temp_limits"]:
            sensor["temp_limits"]["warning_delta"] = 3.0
        if "warning_delta" not in sensor["hum_limits"]:
            sensor["hum_limits"]["warning_delta"] = 5.0
    
    return new_config
```

## 9. Запуск и развёртывание

### 9.1 Локальный запуск (разработка)

```bash
# Установка зависимостей
pip install -r requirements.txt

# Запуск всех подсистем (в разных терминалах)
python -m poller.app --port 5001
python -m archiver.app --port 5002
python -m visualizer.app --port 5000
python -m telegram_bot.bot
```

### 9.2 Docker Compose

```yaml
version: '3.8'

services:
  poller:
    build:
      context: .
      dockerfile: Dockerfile
    command: python -m poller.app
    ports:
      - "5001:5001"
    volumes:
      - ./data:/app/data
      - /dev:/dev
    privileged: true  # Для доступа к COM-портам
    restart: unless-stopped

  archiver:
    build:
      context: .
      dockerfile: Dockerfile
    command: python -m archiver.app
    ports:
      - "5002:5002"
    volumes:
      - ./data:/app/data
    depends_on:
      - poller
    restart: unless-stopped

  visualizer:
    build:
      context: .
      dockerfile: Dockerfile
    command: python -m visualizer.app
    ports:
      - "5000:5000"
    volumes:
      - ./data:/app/data
    depends_on:
      - poller
      - archiver
    restart: unless-stopped

  telegram_bot:
    build:
      context: .
      dockerfile: Dockerfile
    command: python -m telegram_bot.bot
    volumes:
      - ./data:/app/data
    depends_on:
      - archiver
    restart: unless-stopped
```
