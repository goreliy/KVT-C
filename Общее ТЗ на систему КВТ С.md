## 1. Общие сведения

### 1.1 Назначение системы

Комплект измерения температуры и влажности "КВТ" предназначен для автоматического измерения температуры и влажности датчиками С2000-ВТ / С2000-ВТИ (Болид) и дальнейшей обработки, хранения с привязкой по времени и визуализации.

Комплект рассчитан на работу с **одним преобразователем интерфейсов С2000-ПП** (Болид), который обеспечивает связь между шиной RS-485 (протокол «Орион») и Modbus RTU.

**Ссылки:**
- Датчик С2000-ВТ: https://bolid.ru/production/s2000-vt.html
- Датчик С2000-ВТИ: https://bolid.ru/production/s2000-vti.html
- Преобразователь С2000-ПП: https://bolid.ru/production/s2000-pp.html

### 1.2 Масштабируемость системы

Система поддерживает до **256 датчиков** С2000-ВТ / С2000-ВТИ на одном С2000-ПП:

- Датчики можно добавлять по одному или группами
- Датчики можно удалять в любой момент
- Максимальное количество датчиков: **256** (ограничение адресного пространства С2000-ПП)
- Каждый датчик занимает 2 адреса Modbus (температура + влажность), итого до 512 адресов
- Рекомендуемые конфигурации для типовых решений:

| Конфигурация | Количество датчиков | Адреса Modbus |
|--------------|---------------------|---------------|
| КВТ-10 | до 10 | 20 адресов |
| КВТ-20 | до 20 | 40 адресов |
| КВТ-40 | до 40 | 80 адресов |
| КВТ-60 | до 60 | 120 адресов |
| КВТ-256 | до 256 | 512 адресов |
| Произвольная | N датчиков (≤256) | 2×N адресов |

### 1.3 Целевая платформа

- **Основная:** ARM v7 4-ядерный контроллер
- **Совместимость:** Linux x86_64, Windows (ПК, серверы)
- **Контейнеризация:** Docker

### 1.4 Технологический стек

- Python 3.8+
- Flask (веб-фреймворк)
- pyserial (Modbus RTU кадры формируются вручную для точного TX/RX-лога)
- SQLite / PostgreSQL (архивная БД)
- HTML/CSS/JS (фронтенд)
- python-telegram-bot (Telegram Bot API)
- matplotlib (генерация графиков)

## 3. Подсистема 1: Modbus Poller

### 3.1 Функциональные требования

- Опрос регистров функцией 0x04 (Read Input Registers)
- **Адреса регистров значений:** 30000 + N (Input Registers)
- **Адреса регистров статусов:** 40000 + N (Holding Registers)
- Чётный адрес - температура, нечётный - влажность
- Непрерывный опрос без остановки
- Логирование обмена по Modbus
- Настройка параметров COM-порта

### 3.2 Параметры подключения (настраиваемые)

| Параметр | По умолчанию | Диапазон |
|----------|--------------|----------|
| COM-порт | /dev/ttyUSB0 | Список доступных |
| Скорость | 9600 | 1200-115200 |
| Биты данных | 8 | 7, 8 |
| Чётность | None | None, Even, Odd |
| Стоп-биты | 1 | 1, 2 |
| Период опроса | 1000 мс | 100-60000 мс |
| Таймаут | 500 мс | 100-5000 мс |

### 3.3 Структура датчика С2000-ВТ

Один датчик С2000-ВТ занимает 2 адреса Modbus:

**Регистры значений (30000 + N):**
- **Адрес N (чётный):** Температура (°C × 10, знаковое 16-бит)
- **Адрес N+1 (нечётный):** Влажность (% × 10, беззнаковое 16-бит)

**Регистры статусов (40000 + N):**
- **Адрес N (чётный):** Статус канала температуры
- **Адрес N+1 (нечётный):** Статус канала влажности

### 3.4 Формат выходных данных (current.json)

> **Примечание:** Название датчика (`name`) задаётся пользователем в разделе **Настройки системы → Настройки датчиков**. Опросчик получает конфигурацию датчиков из файла `system_config.json`.

### 3.5 Статусы датчиков (коммуникационные)

| Статус | Код | Описание |
|--------|-----|----------|
| ok | 0 | Данные получены успешно |
| timeout | 1 | Таймаут ответа |
| crc_error | 2 | Ошибка CRC |
| exception | 3 | Modbus exception |
| offline | 4 | Датчик недоступен (N попыток) |

### 3.6 Комбинированные статусы (combined_status)

| Статус | Описание |
|--------|----------|
| normal | Значения в норме |
| warning_high_temp | Превышение верхней границы температуры |
| warning_low_temp | Принижение нижней границы температуры |
| warning_high_hum | Превышение верхней границы влажности |
| warning_low_hum | Принижение нижней границы влажности |
| alarm | Критическое отклонение (более X% от границы) |
| no_connection | Нет связи с датчиком |
| guarded | На охране (мониторинг границ активен) |

### 3.9 Конфигурация Modbus Poller (poller_config.json)

```json
{
  "auto_start": true,
  "use_mock_server": false,
  "mock_server_url": "http://127.0.0.1:8000",
  "com_port": "COM8",
  "device_slave_id": 16,
  "baudrate": 9600,
  "bytesize": 8,
  "parity": "N",
  "stopbits": 1,
  "timeout_ms": 500,
  "poll_period_ms": 1000,
  "retry_count": 3,
  "value_register_base": 30000,
  "status_register_base": 40000,
  "log_max_entries": 1000
}
```

> **Примечание:** Список датчиков хранится в `system_config.json` (см. раздел 6).
> Modbus Poller в системе работает по Modbus RTU через COM-порт; `use_mock_server` и `mock_server_url` используются визуализацией для тестового контура (запуск/остановка и переход на страницу Mock Server).
> Poller предоставляет отдельную страницу сервиса (`GET /` на порту Poller) для полного управления: старт/стоп, статус, парный журнал обменов (строка/элемент `system_config.json` -> TX -> RX -> результат), цветовая подсветка строки конфигурации и типа запроса, отдельные окна TX/RX Modbus в HEX-байтах, настройка `device_slave_id` и поиск устройств по Slave ID.
> Поиск устройств выполняется запросом чтения по адресу `40000` (или `status_register_base`), с `timeout_ms`; есть ответ — устройство найдено, нет ответа — не найдено.

## 4. Подсистема 2: Archive Manager

### 4.1 Функциональные требования

- Копирование данных из current.json в архив (по таймеру или по изменению)
- Поддержка нескольких хранилищ: SQLite, PostgreSQL, JSON-файл
- Компрессия данных (схлопывание одинаковых значений)
- Управление размером архива
- Резервирование свободного места на диске
- Автоматическая ротация старых данных

### 4.2 Режимы забора данных

Система архивирования поддерживает два режима забора данных из опросчика Modbus:

#### 4.2.1 Режим по таймеру (periodic)

Архиватор периодически читает файл `current.json` с заданным интервалом.

| Параметр | По умолчанию | Диапазон |
|----------|--------------|----------|
| archive_period_ms | 1000 | 100-60000 мс |

**Особенности:**
- Простая реализация
- Предсказуемая нагрузка на систему
- Возможна потеря данных при периоде архивации > периода опроса

#### 4.2.2 Режим по изменению файла (watch)

Архиватор отслеживает изменения файла `current.json` и забирает данные сразу после обновления.

**Особенности:**
- Гарантированный захват всех данных
- Минимальная задержка архивации
- Нагрузка зависит от частоты опроса

#### 4.2.3 Комбинированный режим (combined)

Сочетает оба подхода: отслеживает изменения файла, но не чаще заданного интервала.

| Параметр | По умолчанию | Описание |
|----------|--------------|----------|
| min_interval_ms | 500 | Минимальный интервал между архивациями |
| max_interval_ms | 5000 | Максимальный интервал (принудительное чтение) |

#### 4.2.4 Конфигурация режимов забора данных

```json
{
  "data_collection": {
    "mode": "combined",
    "source_file": "./data/current.json",
    "periodic": {
      "enabled": false,
      "interval_ms": 1000
    },
    "watch": {
      "enabled": true,
      "debounce_ms": 100
    },
    "combined": {
      "enabled": true,
      "min_interval_ms": 500,
      "max_interval_ms": 5000
    }
  }
}
```

#### 4.2.5 Диаграмма режимов

```mermaid
flowchart LR
    subgraph periodic [Режим periodic]
        T1[Таймер] -->|каждые N мс| R1[Чтение файла]
    end
    
    subgraph watch [Режим watch]
        F1[Изменение файла] -->|событие| R2[Чтение файла]
    end
    
    subgraph combined [Режим combined]
        F2[Изменение файла] -->|событие| D[Debounce]
        T2[Max таймер] -->|fallback| D
        D -->|min interval| R3[Чтение файла]
    end
```

### 4.4 Алгоритм компрессии данных

Для экономии места одинаковые последовательные значения "схлопываются":

```
Исходные данные (каждую секунду):
  15:00:00 - 23.5°C
  15:00:01 - 23.5°C
  15:00:02 - 23.5°C
  15:00:03 - 23.6°C
  15:00:04 - 23.6°C

Сжатые данные:
  15:00:00 - 23.5°C (duration: 3s, count: 3)
  15:00:03 - 23.6°C (duration: 2s, count: 2)
```

### 4.5 Схема БД SQLite/PostgreSQL

```sql
-- Таблица датчиков
CREATE TABLE sensors (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    modbus_slave_id INTEGER,
    modbus_addr_temp INTEGER,
    modbus_addr_hum INTEGER,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Таблица измерений (со схлопыванием)
CREATE TABLE measurements (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sensor_id INTEGER REFERENCES sensors(id),
    timestamp_start TIMESTAMP NOT NULL,
    timestamp_end TIMESTAMP NOT NULL,
    duration_seconds INTEGER,
    sample_count INTEGER DEFAULT 1,
    temperature REAL,
    humidity REAL,
    temp_status TEXT,
    hum_status TEXT,
    combined_status TEXT
);

-- Индекс для быстрого поиска
CREATE INDEX idx_sensor_time ON measurements(sensor_id, timestamp_start);

-- Таблица событий (тревоги, квитирование)
CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sensor_id INTEGER REFERENCES sensors(id),
    timestamp TIMESTAMP NOT NULL,
    event_type TEXT NOT NULL,
    value REAL,
    threshold REAL,
    acknowledged BOOLEAN DEFAULT FALSE,
    acknowledged_at TIMESTAMP,
    acknowledged_by TEXT,
    comment TEXT
);

-- Журнал температур и влажности (агрегированные данные по периодам)
CREATE TABLE temperature_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sensor_id INTEGER REFERENCES sensors(id),
    period_type TEXT NOT NULL,          -- 'hour', 'day', 'week'
    period_start TIMESTAMP NOT NULL,
    period_end TIMESTAMP NOT NULL,
    temp_min REAL,
    temp_max REAL,
    temp_avg REAL,
    hum_min REAL,
    hum_max REAL,
    hum_avg REAL,
    sample_count INTEGER DEFAULT 0
);

CREATE INDEX idx_temp_log_sensor_period ON temperature_log(sensor_id, period_type, period_start);

-- Журнал превышений (фиксация каждого выхода за границы)
CREATE TABLE threshold_violations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sensor_id INTEGER REFERENCES sensors(id),
    started_at TIMESTAMP NOT NULL,
    ended_at TIMESTAMP,
    duration_seconds INTEGER,
    parameter TEXT NOT NULL,            -- 'temperature', 'humidity'
    violation_type TEXT NOT NULL,       -- 'warning_high', 'warning_low', 'alarm_high', 'alarm_low'
    value_at_start REAL,
    value_peak REAL,
    threshold REAL,
    acknowledged BOOLEAN DEFAULT FALSE,
    acknowledged_at TIMESTAMP,
    acknowledged_by TEXT,
    comment TEXT
);

CREATE INDEX idx_violations_sensor ON threshold_violations(sensor_id, started_at);
CREATE INDEX idx_violations_open ON threshold_violations(ended_at) WHERE ended_at IS NULL;

-- Таблица статистики архива
CREATE TABLE archive_stats (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    total_records INTEGER,
    disk_usage_bytes INTEGER,
    compression_ratio REAL
);
```

### 4.6 Формат JSON-архива (archive.json)

```json
{
  "version": "1.0",
  "created_at": "2026-01-01T00:00:00",
  "last_updated": "2026-01-14T15:30:45",
  "compression_enabled": true,
  "sensors": {
    "1": {
      "name": "ХРАН. № 1",
      "measurements": [
        {
          "ts": "2026-01-14T15:00:00",
          "te": "2026-01-14T15:00:03",
          "d": 3,
          "n": 3,
          "t": 23.5,
          "h": 45.2,
          "s": "normal"
        }
      ],
      "events": []
    }
  }
}
```

**Расшифровка полей:**
- `ts` - timestamp_start
- `te` - timestamp_end
- `d` - duration (секунды)
- `n` - количество измерений

- `h` - влажность

- Мини-график за последний час

#### 5.1.3 Детальный просмотр датчика

- График температуры/влажности

- Настройка архивирования
- Настройка уведомлений

#### 5.1.5 Уведомления

- Email при превышении/принижении границ
- Telegram-бот для интерактивного получения данных
- Уведомления в Telegram при превышениях и тревогах
- Периодические отчёты (Email/Telegram) с настраиваемой регулярностью
- Графики за период в отчётах
- Настройка расписания отчётов: ежечасно / ежедневно / еженедельно / ежемесячно

#### 5.1.6 Расширенный журнал

- Журнал событий (тревоги, квитирование, изменения конфигурации)
- Журнал температур и влажности с агрегацией по часам/дням/неделям (min/max/avg)
- Журнал превышений границ с длительностью, пиковыми значениями и статусом квитирования
- Фильтрация по датчику, типу события, периоду, статусу

#### 5.1.7 План помещения

- Отдельная вкладка «План помещения» в навигации
- Поддержка нескольких планов и подпланов (иерархия)
- Загрузка подложки плана в виде растрового изображения (PNG, JPG, BMP, WebP) или SVG-файла
- Размещение датчиков на плане методом drag & drop из палитры
- Перетаскивание маркеров датчиков по плану
- Отображение текущих значений (температура, влажность) на маркерах в реальном времени
- Цветовая индикация статуса датчика на маркере (норма / предупреждение / тревога / нет связи)
- Удаление датчика с плана (возврат в палитру)
- Создание подпланов (дочерних планов) для детализации отдельных зон
- Удаление плана с каскадным удалением подпланов
- Сохранение конфигурации планов и расположения датчиков в файле `floorplan_config.json`

#### 5.1.8 Оформление и темы

- Поддержка двух тем оформления: тёмная (по умолчанию) и светлая
- Переключение темы кнопкой в навигационной панели (мгновенное применение)
- Настройка цветов для каждой темы отдельно через страницу «Настройки → Оформление»
- Настраиваемое название приложения (отображается в навигации и заголовке вкладки браузера, макс. 50 символов, по умолчанию «КВТ Мониторинг»)
- Настраиваемые цвета (для каждой темы):
  - Фон страницы, фон карточек, фон полей ввода
  - Основной и вторичный текст
  - Цвет границ
  - Статусные цвета: норма, охрана/акцент, предупреждение, тревога, нет связи
  - Фон навигации, цвет логотипа
- Сброс цветов темы к значениям по умолчанию
- Предпросмотр статусных цветов на странице настроек

```
Требуется квитирование!
```

### 6.4 Формат регулярного отчёта

Отчёт включает:

1. Сводную таблицу по всем датчикам (текущие значения, статусы)
2. Диапазоны температур/влажности за период (min / max / avg)
3. Количество и длительность превышений за период
4. Графики температуры и влажности (изображения)

Пример текстовой части:

```
📊 ЕЖЕДНЕВНЫЙ ОТЧЁТ КВТ
Период: 12.01.2026 08:00 — 13.01.2026 08:00

📍 ХРАН. № 1
  Температура: 21.3 .. 25.1°C (avg 23.2°C)
  Влажность: 40.0 .. 52.3% (avg 45.8%)
  Превышений: 2 (общая длительность 28 мин)

📍 ХРАН. № 3
  Температура: 3.1 .. 7.8°C (avg 5.2°C)
  Влажность: 35.2 .. 62.1% (avg 48.7%)
  Превышений: 0

Всего превышений за период: 2
```

После текста отправляются графики (изображения PNG).

### 6.5 Генерация графиков

Бот генерирует графики с помощью matplotlib:

- Линейный график температуры и влажности за период
- Отображение границ (warning/alarm) горизонтальными линиями
- Подсветка зон превышений
- Поддержка периодов: 1 час, 6 часов, 24 часа, 7 дней, 30 дней
- Формат вывода: PNG изображение

### 6.6 Планировщик отчётов

Планировщик на базе APScheduler поддерживает:

| Тип | Описание | Настройки |
|-----|----------|-----------|
| hourly | Каждый час | minute — минута отправки (0-59) |
| daily | Ежедневно | time — время отправки (HH:MM) |
| weekly | Еженедельно | day_of_week + time |
| monthly | Ежемесячно | day_of_month + time |

Каждый тип отчёта можно включить/выключить независимо. Расписание настраивается через:
- Файл `notifications.json` (раздел `telegram.reports.schedule`)
- Команду бота `/schedule`
- Веб-интерфейс: `/settings/reports`

### 7.2 Версионность конфигурации

### 7.5 Валидация конфигурации

При изменении конфигурации выполняется валидация:

| Проверка | Описание |
|----------|----------|
| Уникальность ID | ID датчика должен быть уникальным |
| Уникальность адресов | Адреса Modbus не должны пересекаться |
| Границы значений | min < max для всех лимитов |
| Обязательные поля | name, modbus_slave_id, адреса |
| Допустимые значения | slave_id: 1-247, адреса: 0-65535 |

### 7.6 Миграция конфигурации

При изменении схемы конфигурации (config_schema_version) система автоматически мигрирует старые конфигурации:

```python
# Пример миграции с версии 0.9 на 1.0
def migrate_0_9_to_1_0(old_config):
    new_config = old_config.copy()
    new_config["config_schema_version"] = "1.0"
    
    # Добавляем новые обязательные поля
    for sensor in new_config["sensors"]:
        if "warning_delta" not in sensor["temp_limits"]:
            sensor["temp_limits"]["warning_delta"] = 3.0
        if "warning_delta" not in sensor["hum_limits"]:
            sensor["hum_limits"]["warning_delta"] = 5.0
    
    return new_config
```
