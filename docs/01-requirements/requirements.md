# Документ требований

## Введение

Система КВТ (Комплект контроля температуры и влажности) предназначена для автоматического измерения, архивирования и визуализации данных температуры и влажности с датчиков С2000-ВТ/С2000-ВТИ (Болид) через преобразователь С2000-ПП по протоколу Modbus RTU. Система состоит из независимых подсистем: Modbus Poller, Archive Manager, Web Visualizer (включая журнал учёта), OPC UA Server, MQTT Bridge, а также специфицированных на будущее Telegram Bot и Report Generator. Целевая платформа — ARM v7 4-ядерный контроллер, с совместимостью Linux x86_64 и Windows. Штатное развёртывание — единой точкой запуска `run_kvt.py`.

> **О статусе требований.** Часть требований этого документа относится к нереализованным
> подсистемам: **Требования 9 (email-уведомления), 10–11 (Telegram Bot), 14 (генератор отчётов),
> 16 (Docker)** — специфицированы, но кодом не реализованы. Требование 15.3 (OPC UA Historical
> Access) также не реализовано. Сводная таблица состояния — в
> [индексе документации](../README.md). Требования не удалены: они остаются целевыми.

## Глоссарий

- **КВТ (KVT_System)**: Комплект контроля температуры и влажности — полная система мониторинга
- **Modbus_Poller**: Подсистема опроса датчиков по протоколу Modbus RTU через RS-485 (порт 5001)
- **Archive_Manager**: Подсистема архивирования, компрессии и хранения измерений (порт 5002)
- **Web_Visualizer**: Подсистема веб-интерфейса для визуализации данных и управления настройками (порт 5000)
- **Telegram_Bot**: Подсистема Telegram-бота для уведомлений, команд и регулярных отчётов
- **Report_Generator**: Подсистема автоматической генерации и сохранения отчётов по расписанию (PDF/HTML/CSV) на диск (порт 5003)
- **OPC_UA_Server**: Подсистема OPC UA 2.0, предоставляющая текущие и архивные данные внешним клиентам по протоколу OPC UA (порт 4840)
- **MQTT_Bridge**: Подсистема двунаправленного обмена данными по MQTT: публикация текущих значений в топики брокера и приём внешних значений и команд (порт брокера по умолчанию 1883)
- **Журнал учёта (Logbook)**: Электронный аналог бумажного журнала складского учёта в составе Web_Visualizer: суточные min/max/avg по выбранным датчикам с ежедневным подтверждением (подписью) оператора
- **С2000-ВТ**: Датчик температуры и влажности производства Болид
- **С2000-ВТИ**: Датчик температуры и влажности с индикацией производства Болид
- **С2000-ПП**: Преобразователь интерфейсов RS-485 / Modbus RTU производства Болид
- **current.json**: Файл с текущими значениями датчиков, обновляемый Modbus_Poller
- **modbus_log.json**: Файл лога Modbus-обмена (кольцевой буфер, макс. 1000 записей)
- **archive.json**: Файл JSON-архива измерений в сокращённом формате
- **system_config.json**: Главный конфигурационный файл системы — единственный источник истины для списка датчиков и настроек, используемый всеми подсистемами
- **poller_config.json**: Конфигурация параметров COM-порта и опроса (без списка датчиков)
- **archive_config.json**: Конфигурация режимов сбора, хранилищ, компрессии и ротации данных
- **notifications.json**: Конфигурация Email SMTP, Telegram-уведомлений, per-sensor настроек и расписания отчётов
- **report_config.json**: Конфигурация расписания генерации отчётов, форматов и директории сохранения
- **opcua_config.json**: Конфигурация OPC UA endpoint, порта, security и аутентификации
- **layout.json**: Конфигурация расположения плашек датчиков на мнемосхеме
- **floorplan_config.json**: Конфигурация планов помещений и позиций датчиков на планах
- **theme_config.json**: Конфигурация тем оформления, цветов и названия приложения
- **mnemo_tree.json**: Конфигурация «дерева датчиков» на мнемосхеме — ветки, подветки и привязанные к ним датчики
- **Конфигурационный архив**: ZIP-пакет для передачи на завод и восстановления настроек; содержит `manifest.json`, JSON-конфиги, картинки планов и диагностические снимки работы системы
- **availability_daily.json**: Суточный учёт доступности линий опроса (ping, % доступности) и датчиков (число полученных снимков)
- **Дерево датчиков**: Настраиваемая иерархическая группировка датчиков на мнемосхеме; в корне ветки выводятся название и текущий min-max температуры/влажности
- **Компрессия данных**: Алгоритм схлопывания последовательных одинаковых значений (в пределах tolerance) для экономии места
- **Квитирование**: Подтверждение оператором факта ознакомления с событием или тревогой
- **Мнемосхема**: Главный экран Web_Visualizer с плашками датчиков на фоновой подложке
- **Плашка датчика**: Визуальный элемент на мнемосхеме, отображающий текущие значения и статус датчика
- **План помещения**: Страница с размещением маркеров датчиков на загруженном изображении/SVG плана
- **Превышение границ (violation)**: Событие выхода измеренного значения за установленные пределы (warning или alarm)
- **combined_status**: Комбинированный статус датчика: normal, warning_high_temp, warning_low_temp, warning_high_hum, warning_low_hum, alarm, no_connection, guarded
- **Коммуникационный статус**: Статус связи с датчиком: ok (0), timeout (1), crc_error (2), exception (3), offline (4)

## Требования

### Требование 1: Опрос датчиков по Modbus RTU

**Пользовательская история:** Как оператор, я хочу, чтобы система автоматически опрашивала датчики температуры и влажности по Modbus RTU, чтобы я всегда имел актуальные данные измерений.

#### Критерии приёмки

1. КОГДА оператор запускает Modbus_Poller, Modbus_Poller ДОЛЖЕН начать циклический опрос всех настроенных датчиков из system_config.json функцией Modbus 0x03 (Read Holding Registers) с настраиваемым периодом от 100 мс до 60000 мс.
2. ПОКА Modbus_Poller работает, Modbus_Poller ДОЛЖЕН читать регистры значений по базовому адресу 30000+N (чётный адрес — температура как знаковое 16-бит, нечётный — влажность как беззнаковое 16-бит) и регистры статусов по базовому адресу 40000+N для каждого настроенного датчика.
3. КОГДА Modbus_Poller получает валидный ответ от датчика, Modbus_Poller ДОЛЖЕН конвертировать сырые 16-битные значения регистров температуры и влажности как знаковое число в дополнительном коде с фиксированной точкой Q8.8 (`smallint / 256`) и записать результат в current.json в течение 50 мс.
4. ЕСЛИ датчик не отвечает в пределах настроенного таймаута (100–5000 мс), ТО Modbus_Poller ДОЛЖЕН пометить статус датчика как "timeout" и повторить запрос до настроенного количества попыток (по умолчанию 3), после чего пометить датчик как "offline".
5. ПОКА Modbus_Poller работает, Modbus_Poller ДОЛЖЕН логировать каждый Modbus TX/RX фрейм с меткой времени, направлением, точными сырыми HEX-байтами и разобранным описанием в modbus_log.json, а также формировать парный журнал обменов `exchange_queue`, где одна строка связывает источник из `system_config.json`, TX, RX и результат ответа.
6. КОГДА Modbus_Poller записывает данные в current.json, Modbus_Poller ДОЛЖЕН включить в файл: метку времени опроса, параметры подключения (COM-порт, скорость), массив датчиков (id, name, modbus_slave_id, адреса, значения температуры и влажности с raw-данными и статусами, combined_status) и статистику опроса (total_polls, successful_polls, failed_polls, last_error).
7. ПОКА Modbus_Poller работает, Modbus_Poller ДОЛЖЕН вычислять combined_status каждого датчика на основе границ из system_config.json: "normal" при значениях в пределах нормы, "warning_high_temp"/"warning_low_temp"/"warning_high_hum"/"warning_low_hum" при выходе за warning-границу, "alarm" при выходе за alarm-границу, "no_connection" при отсутствии связи, "guarded" при активном мониторинге границ.

### Требование 2: Настройка параметров подключения Modbus

**Пользовательская история:** Как оператор, я хочу настраивать параметры подключения Modbus (COM-порт, скорость, чётность, таймаут), чтобы система работала с моей конкретной аппаратной конфигурацией.

#### Критерии приёмки

1. Modbus_Poller ДОЛЖЕН поддерживать настройку COM-порта, скорости (1200–115200), битов данных (7 или 8), чётности (None, Even, Odd), стоп-битов (1 или 2), периода опроса (100–60000 мс), таймаута (100–5000 мс) и количества повторов (по умолчанию 3) через poller_config.json.
2. КОГДА оператор изменяет параметры подключения Modbus через REST API (POST /api/poller/config), Modbus_Poller ДОЛЖЕН применить новые параметры и перезапустить цикл опроса в течение 2 секунд.
3. КОГДА оператор запрашивает доступные COM-порты (GET /api/poller/ports), Modbus_Poller ДОЛЖЕН вернуть список всех обнаруженных последовательных портов на хост-системе.
4. КОГДА оператор отправляет команду запуска (POST /api/poller/start), Modbus_Poller ДОЛЖЕН начать циклический опрос датчиков.
5. КОГДА оператор отправляет команду остановки (POST /api/poller/stop), Modbus_Poller ДОЛЖЕН прекратить циклический опрос датчиков.
6. КОГДА оператор отправляет команду перезагрузки конфигурации (POST /api/poller/reload), Modbus_Poller ДОЛЖЕН перечитать список датчиков из system_config.json и применить изменения без перезапуска подсистемы.
7. Modbus_Poller ДОЛЖЕН хранить и применять в `poller_config.json` поля `value_register_base`, `status_register_base` и `log_max_entries`; изменения этих полей через `/api/poller/config` ДОЛЖНЫ применяться без ручного редактирования файлов.
8. Modbus_Poller ДОЛЖЕН поддерживать параметр `device_slave_id` в `poller_config.json` для задания адреса Modbus-устройства (1–247), используемого в цикле опроса.
9. Modbus_Poller ДОЛЖЕН предоставлять endpoint `GET /api/poller/scan?start_id=&end_id=&timeout_ms=` для поиска доступных Modbus-устройств на выбранном COM-порту по диапазону Slave ID с заданным таймаутом.
10. Web_Visualizer ДОЛЖЕН предоставлять на странице `/settings/poller` переключатель `use_mock_server` для тестового режима, кнопки запуска/остановки Mock Server и кнопку перехода на страницу Mock Server.
11. КОГДА оператор нажимает запуск Mock Server из основной визуализации, система ДОЛЖНА запустить тестовый Mock Server и вернуть его статус; КОГДА оператор нажимает остановку — система ДОЛЖНА остановить Mock Server и обновить статус.
12. КОГДА включён `use_mock_server`, Visualizer ДОЛЖЕН сохранять параметры подключения к Mock Server (`mock_server_url`) в `poller_config.json` для использования в тестовом контуре без изменения протокола Modbus Poller.
13. Modbus_Poller продолжает работать только по Modbus RTU через COM-порт; использование Mock Server в данном ТЗ относится к тестовому контуру визуализации и отладки, а не к переходу Poller на Modbus TCP.
14. Modbus_Poller ДОЛЖЕН иметь собственную веб-страницу сервиса на порту Poller (`GET /`) с полным интерфейсом управления: просмотр статуса, просмотр парного журнала обменов (одна строка = строка/элемент конфигурации + TX + RX + результат), цветовую подсветку строки конфигурации и типа запроса, отдельные окна TX/RX Modbus в байтовом (HEX) виде, изменение `device_slave_id`, запуск/остановка опроса и запуск сканирования устройств.
15. При сканировании устройств Poller ДОЛЖЕН отправлять запрос чтения по адресу `40000` (или `status_register_base` из конфигурации) с заданным `timeout_ms`; отсутствие ответа означает «устройство не найдено», наличие валидного ответа означает «устройство найдено» с указанием Slave ID.
16. Каждая линия опроса (`poll_ports[]`) ДОЛЖНА иметь собственные параметры опроса: `poll_period_ms` (0 = общий), `timeout_ms` и `retry_count` (-1 = общий); пер-линейные значения переопределяют общие.
17. КОГДА датчик не отвечает `retry_count` повторов подряд, Modbus_Poller ДОЛЖЕН перевести этот датчик в «медленный цикл» (одна попытка раз в `slow_poll_period_ms` линии, по умолчанию 30000 мс), оставив его в выдаче current.json (последний снимок/offline, признак `slow_poll: true`); ПРИ первом успешном ответе датчик ДОЛЖЕН автоматически вернуться в обычный цикл. Датчик НЕ ДОЛЖЕН выпадать из опроса ни при каких условиях.
18. Опрос НЕ ДОЛЖЕН останавливаться самостоятельно ни при каких ошибках (таймауты, сбои порта, ошибки записи журнала, переполнение лога, внутренние исключения): цикл worker полностью защищён от исключений, watchdog каждые 5 секунд пересоздаёт упавший worker, а журнал Modbus ограничен `log_max_entries` целиком (записи + TX + RX + обмены) и перезатирается по кольцу. Единственный способ остановки опроса — явная команда оператора.
19. Поле «COM-порт» в редакторе линии ДОЛЖНО поддерживать выбор из доступных портов системы (галочка «Выбрать из доступных» → список из GET /api/poller/ports: на Windows `COMx`, на Linux `/dev/tty*`); tty-имена, введённые без пути, ДОЛЖНЫ автоматически дополняться префиксом `/dev/` (например, `ttyUSB0` → `/dev/ttyUSB0`) как на клиенте, так и при валидации конфигурации.

### Требование 3: Архивирование данных

**Пользовательская история:** Как оператор, я хочу, чтобы данные измерений автоматически архивировались, чтобы я мог просматривать исторические тренды и генерировать отчёты.

#### Критерии приёмки

1. ПОКА Archive_Manager работает, Archive_Manager ДОЛЖЕН периодически читать current.json и сохранять измерения в настроенное хранилище данных (SQLite, PostgreSQL или JSON-файл).
2. Archive_Manager ДОЛЖЕН поддерживать три режима сбора данных: periodic (по таймеру с настраиваемым интервалом 100–60000 мс), watch (по изменению файла с debounce) и combined (по изменению файла с ограничениями минимального и максимального интервала).
3. КОГДА компрессия включена, Archive_Manager ДОЛЖЕН схлопывать последовательные измерения с одинаковыми значениями (в пределах настроенного допуска: 0.1 °C для температуры, 0.5 % для влажности) в одну запись с меткой начала, меткой конца, длительностью и количеством выборок.
4. ПОКА объём архивного хранилища превышает настроенный максимум, Archive_Manager ДОЛЖЕН применять политики хранения: сырые данные за 24 часа, агрегация по 1 минуте за 1–7 дней, агрегация по 5 минут за 7–30 дней, агрегация по 1 часу за 30–365 дней, агрегация по 1 дню свыше 1 года.
5. ЕСЛИ свободное дисковое пространство падает ниже настроенного минимума (по умолчанию 200 МБ), ТО Archive_Manager ДОЛЖЕН удалить старейшие архивные данные до восстановления достаточного объёма.
6. Archive_Manager ДОЛЖЕН работать как отдельный сервис (Flask, порт 5002) и формировать архив измерений, журнал событий и журнал превышений из РЕАЛЬНЫХ данных current.json, заменяя демонстрационные data/archive.json и data/events.json в роли источника для визуализации.
7. КОГДА измеренное значение выходит за warning- или alarm-границу, вычисленную из temp_limits/hum_limits (min/max ± warning_delta/alarm_delta) в system_config.json, Archive_Manager ДОЛЖЕН создать открытую запись в threshold_violations (parameter, violation_type, value_at_start, started_at) и соответствующее событие в events; КОГДА значение возвращается в норму, Archive_Manager ДОЛЖЕН закрыть запись (ended_at, duration_seconds, value_peak). Температура и влажность оцениваются независимо.
8. ПРИ первом запуске с пустым хранилищем Archive_Manager ДОЛЖЕН выполнить однократную миграцию существующих data/archive.json и data/events.json в выбранное хранилище (SQLite по умолчанию), сохранив идентификаторы и статус квитирования событий, и пометить миграцию выполненной, чтобы не повторять её.
9. Archive_Manager ДОЛЖЕН выбирать активное хранилище согласно archive_config.json (SQLite — основное, PostgreSQL — опционально, JSON-файл — fallback); критерии переключения на fallback определены в Требовании 19.2.
10. КОГДА archive_config.json изменён через Web_Visualizer (POST к Archive_Manager или visualizer-proxy), Archive_Manager ДОЛЖЕН применить новый режим сбора, параметры хранилища, компрессии и ротации без ручного редактирования файла и без перезапуска процесса.

### Требование 4: Управление датчиками

**Пользовательская история:** Как оператор, я хочу добавлять, редактировать и удалять датчики через веб-интерфейс, чтобы управлять конфигурацией мониторинга без ручного редактирования файлов.

#### Критерии приёмки

1. КОГДА оператор отправляет нового датчика через POST /api/sensors, Web_Visualizer ДОЛЖЕН валидировать данные датчика (уникальный ID, уникальные адреса Modbus, валидный slave ID 1–247, min < max для границ, обязательные поля: name, modbus_slave_id, адреса) и добавить датчик в system_config.json.
2. КОГДА оператор обновляет датчик через PUT /api/sensors/{id}, Web_Visualizer ДОЛЖЕН валидировать изменения и обновить запись датчика в system_config.json.
3. КОГДА оператор удаляет датчик через DELETE /api/sensors/{id}, Web_Visualizer ДОЛЖЕН удалить датчик из system_config.json.
4. КОГДА оператор добавляет несколько датчиков через POST /api/sensors/batch, Web_Visualizer ДОЛЖЕН валидировать каждый датчик и добавить все датчики в system_config.json одной операцией.
5. КОГДА оператор удаляет несколько датчиков через DELETE /api/sensors/batch, Web_Visualizer ДОЛЖЕН удалить указанные датчики из system_config.json одной операцией.
6. КОГДА любое изменение конфигурации датчиков сохраняется, Web_Visualizer ДОЛЖЕН инкрементировать config_version, записать изменение в update_history и создать резервную копию в data/config/backups/.

4. Report_Generator ДОЛЖЕН сохранять сгенерированные отчёты в настраиваемую директорию (по умолчанию: data/reports/) с соглашением об именовании, включающим тип отчёта, период и метку времени (например, daily_2026-01-14_080000.pdf).
5. ПОКА директория хранения отчётов превышает настроенный максимальный размер или количество файлов, Report_Generator ДОЛЖЕН удалять старейшие файлы отчётов согласно настроенной политике хранения (по умолчанию: хранить отчёты 365 дней).
6. КОГДА оператор запрашивает ручную генерацию отчёта через Web_Visualizer (/settings/reports) или REST API (POST /api/reports/generate), Report_Generator ДОЛЖЕН немедленно сгенерировать отчёт за указанный период и в указанном формате.

### Требование 15: OPC UA сервер

**Пользовательская история:** Как системный интегратор, я хочу, чтобы система КВТ предоставляла текущие и исторические данные датчиков через OPC UA 2.0, чтобы внешние SCADA-системы и другие OPC UA клиенты могли потреблять данные.

#### Критерии приёмки

1. OPC_UA_Server ДОЛЖЕН предоставлять адресное пространство OPC UA с корневым объектом `KVT` и папками `KVT/System` (метаданные сервера), `KVT/PollPorts/PollPort_<id>` (состояние линий опроса) и `KVT/Sensors/Sensor_<id>` (переменные датчика: температура, влажность, комбинированный статус, метка времени, привязка к линии; при включённом `fields.limits` — границы). NodeId ДОЛЖНЫ быть стабильными и строиться по id датчика: `KVT.Sensors.<id>.Temperature`, `.Humidity`, `.CombinedStatus`, `.Timestamp`, `.PollPortId`.
2. ПОКА OPC_UA_Server работает, OPC_UA_Server ДОЛЖЕН обновлять значения переменных датчиков из текущего среза (current.json) с настраиваемым интервалом публикации (`publishing.update_interval_ms`, по умолчанию 1000 мс); при отсутствии или устаревании значения числовой узел ДОЛЖЕН публиковаться с качеством BadNoData.
3. OPC_UA_Server ДОЛЖЕН поддерживать интерфейс OPC UA Historical Access (HA), позволяющий клиентам читать архивные данные температуры и влажности для указанного датчика и временного диапазона из хранилища Archive_Manager.
4. OPC_UA_Server ДОЛЖЕН поддерживать настраиваемые через opcua_config.json endpoint, порт (по умолчанию 4840), путь (`/kvt/`) и namespace (`namespace_uri`, по умолчанию `urn:kvt:c:monitoring`); в текущей реализации поддерживается режим безопасности `anonymous_readonly`, а параметры `certificate` и `user_password` (сертификаты, список пользователей) сохраняются в конфиге как заготовки для последующего ужесточения безопасности.
5. КОГДА датчик добавляется/удаляется из system_config.json либо меняется выбор датчиков или полей в opcua_config.json, OPC_UA_Server ДОЛЖЕН перечитать конфигурацию и обновить адресное пространство без перезапуска процесса; смена host/port/endpoint_path/security может требовать перезапуска сервиса.
6. OPC_UA_Server ДОЛЖЕН публиковать тот же нормализованный состав датчиков и те же fallback-значения, что и `/api/current`, и записывать состояние сервиса в `data/opcua_status.json` (state, endpoint, число экспортируемых датчиков, время обновления).
7. OPC_UA_Server ДОЛЖЕН объявлять клиентам (в endpoint URL и ответах discovery) актуальный IP машины вместо self-адресов (`0.0.0.0`/`localhost`/пустой host), сохраняя привязку сокета ко всем интерфейсам; ПРИ смене IP машины сервер ДОЛЖЕН автоматически перепубликовать endpoint. Web_Visualizer ДОЛЖЕН вычислять свежесть статуса (`stale`, `age_seconds`) на сервере по mtime файла статуса, а не по часам браузера.

### Требование 18: Безопасность и защита данных

**Пользовательская история:** Как администратор, я хочу, чтобы система обеспечивала базовую защиту от несанкционированного доступа и утечки данных, чтобы конфигурация и данные мониторинга были защищены.

#### Критерии приёмки

1. Web_Visualizer ДОЛЖЕН поддерживать опциональную HTTP Basic Authentication для доступа к веб-интерфейсу и REST API, настраиваемую через system_config.json.
2. KVT_System ДОЛЖНА хранить пароли и токены (SMTP password, Telegram bot token, PostgreSQL password, OPC UA password) в конфигурационных файлах в зашифрованном виде или через переменные окружения, а REST API ДОЛЖЕН маскировать эти значения при выдаче конфигурации (заменять на "****").
3. КОГДА оператор загружает файл изображения через Web_Visualizer (фон мнемосхемы, план помещения), Web_Visualizer ДОЛЖЕН валидировать тип файла по содержимому (magic bytes), ограничивать размер файла (максимум 10 МБ) и сохранять файл с сгенерированным именем для предотвращения path traversal атак.
4. Web_Visualizer ДОЛЖЕН устанавливать HTTP-заголовки безопасности: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Content-Security-Policy с ограничением источников скриптов.
5. КОГДА Modbus_Poller записывает current.json, Modbus_Poller ДОЛЖЕН использовать атомарную запись (запись во временный файл с последующим переименованием) для предотвращения чтения неполных данных другими подсистемами.
6. KVT_System ДОЛЖНА валидировать все входные данные REST API (JSON-схемы, диапазоны значений, длины строк) и возвращать HTTP 400 с описанием ошибки при невалидных данных.
7. ПОКА система работает в Docker, контейнер Modbus_Poller ДОЛЖЕН использовать маппинг конкретных устройств (--device) вместо privileged mode, когда это возможно, для минимизации привилегий.

### Требование 19: Целостность данных и обработка ошибок

**Пользовательская история:** Как оператор, я хочу, чтобы система корректно обрабатывала ошибки и сбои, чтобы данные мониторинга оставались целостными и система продолжала работать при частичных отказах.

#### Критерии приёмки

1. ЕСЛИ Modbus_Poller теряет соединение с COM-портом, ТО Modbus_Poller ДОЛЖЕН перейти в состояние "error" и пытаться переподключиться каждые 5 секунд до восстановления связи.
2. ЕСЛИ Archive_Manager не может записать данные в основное хранилище (SQLite/PostgreSQL) после 3 попыток с экспоненциальной задержкой, ТО Archive_Manager ДОЛЖЕН переключиться на JSON-хранилище как fallback.
3. ЕСЛИ Web_Visualizer не может получить данные от Modbus_Poller API, ТО Web_Visualizer ДОЛЖЕН отобразить последние известные данные с индикатором «данные устарели» и меткой времени последнего успешного обновления.
4. ЕСЛИ Telegram_Bot не может отправить сообщение через Telegram API, ТО Telegram_Bot ДОЛЖЕН повторить отправку с экспоненциальной задержкой (1 с, 2 с, 4 с, максимум 60 с).
5. ЕСЛИ Report_Generator не может сгенерировать PDF, ТО Report_Generator ДОЛЖЕН переключиться на HTML-формат как fallback и записать ошибку в лог.
6. ЕСЛИ OPC_UA_Server не может прочитать current.json, ТО OPC_UA_Server ДОЛЖЕН вернуть последние известные значения с OPC UA StatusCode Bad_OutOfDate.
7. КОГДА Archive_Manager обнаруживает повреждённый current.json (невалидный JSON), Archive_Manager ДОЛЖЕН пропустить текущий цикл архивации и записать ошибку в лог без прерывания работы.
8. ЕСЛИ MQTT_Bridge не может подключиться к брокеру, ТО MQTT_Bridge НЕ ДОЛЖЕН завершаться: состояние отражается в `data/mqtt_status.json`, попытки подключения повторяются автоматически.

### Требование 20: MQTT Bridge

**Пользовательская история:** Как системный интегратор, я хочу получать текущие данные датчиков по MQTT и отправлять в систему внешние значения и команды, чтобы интегрировать КВТ с IoT-платформами и системами верхнего уровня.

#### Критерии приёмки

1. MQTT_Bridge ДОЛЖЕН публиковать текущие значения датчиков в топики брокера с настраиваемым интервалом (`publishing.interval_ms`, по умолчанию 1000 мс, диапазон 250–60000): полный срез в `{base}/current` при `publish_snapshot=true` и каждый датчик в `{base}/sensors/{id}` при `publish_per_sensor=true`.
2. MQTT_Bridge ДОЛЖЕН публиковать состояние сервиса в топик `{base}/status` и в файл `data/mqtt_status.json`.
3. MQTT_Bridge ДОЛЖЕН публиковать тот же нормализованный состав датчиков и те же fallback-значения, что и `/api/current`; полезная нагрузка — JSON в UTF-8.
4. КОГДА `receiving.enabled=true`, MQTT_Bridge ДОЛЖЕН подписываться на `{base}/inbound/sensors/+` и сохранять принятые сообщения в журнал `data/mqtt_inbound.json`, доступный через `GET /api/mqtt/inbound`.
5. КОГДА в топик `{base}/commands/republish` поступает сообщение, MQTT_Bridge ДОЛЖЕН немедленно опубликовать срез, не дожидаясь очередного интервала; КОГДА сообщение поступает в `{base}/commands/ping` — обновить статус.
6. MQTT_Bridge ДОЛЖЕН поддерживать настройку брокера (host, port, keepalive 5–3600 с, client_id, username/пароль), базового топика (без пробелов и wildcard `#`/`+`), QoS 0–2 и retain для публикации, а также TLS (CA, клиентский сертификат и ключ, флаг insecure) через `mqtt_config.json`.
7. Web_Visualizer ДОЛЖЕН предоставлять страницу `/settings/mqtt` для управления всеми настройками и endpoint'ы `GET/POST /api/mqtt/config`, `GET /api/mqtt/status`, `GET /api/mqtt/inbound`, `POST /api/mqtt/reload`; пароль брокера ДОЛЖЕН маскироваться при выдаче через API.
8. MQTT_Bridge ДОЛЖЕН запускаться через `run_kvt.py --service mqtt`; при `--service all` — только при включённом `autostart` в конфигурации.

### Требование 21: Журнал учёта (складская отчётность)

**Пользовательская история:** Как кладовщик, я хочу ежедневно подтверждать своей подписью просмотр суточных показаний по помещениям склада, чтобы вести учёт микроклимата так же, как в бумажном журнале, и предъявлять его при аудите.

#### Критерии приёмки

1. Web_Visualizer ДОЛЖЕН поддерживать настраиваемые журналы учёта (`reports_config.json`): имя, тип (складской/справочный), набор датчиков, состав отображаемых колонок и признак необходимости ежедневного подтверждения.
2. Для журнала и каждой даты Web_Visualizer ДОЛЖЕН показывать по каждому датчику суточные минимум, максимум и среднее температуры и влажности; день идентифицируется датой в формате `YYYY-MM-DD`; источник суточных значений — `data/archive_daily.json` (при отсутствии — агрегация архива).
3. Оператор ДОЛЖЕН подтверждать («расписываться») за рабочий день, выбирая ФИО из управляемого списка операторов (`operators.json`, без пароля); подтверждение фиксирует ФИО, дату и время подтверждения и снимок суточных значений в `data/logbook_signoffs.json`.
4. Подтверждённые записи ДОЛЖНЫ быть неизменяемыми: последующее изменение архивных данных НЕ меняет уже подписанную запись (хранится снимок значений).

7. Web_Visualizer ДОЛЖЕН предоставлять печатный вид журнала за период (`/logbook/{report_id}/print`), пригодный для бумажного аудита: строки по дням с суточными значениями и колонкой подписи (ФИО, дата подтверждения).
8. Web_Visualizer ДОЛЖЕН предоставлять админ-страницу `/settings/reports` для управления журналами, списком операторов и календарём, а также endpoint'ы `GET /api/logbook/daily`, `POST /api/logbook/signoff`, `POST /api/logbook/batch-signoff`, `GET/POST /api/operators`, `GET/POST /api/holidays`.
