# 5. Подсистема 3: Web Visualizer

## 5.1 Функциональные требования

### 5.1.1 Главный экран (мнемосхема)

- Отображение произвольного количества плашек датчиков
- Загрузка фоновой подложки (изображение)
- Перетаскивание плашек (drag & drop)
- Изменение размера плашек
- Сохранение расположения
- Группировка плашек по пользовательским группам
- Редактор групп: создание, переименование, удаление, выбор цвета/сворачивания, перенос датчиков между группами
- Фильтрация и сортировка плашек по линии опроса (`poll_port_id`/`poll_port_name`), группе, статусу и имени
- Отдельная плашка доступности по линии («Доступность Ethernet-линий») на мнемосхеме НЕ выводится. Доступность/ping показываются в карточке каждого датчика, привязанного к Ethernet-линии (см. 5.1.2)
- Дерево датчиков с режимом редактирования (см. 5.1.9)

### 5.1.2 Плашка датчика

- Видимый номер датчика в формате `<имя линии>-<номер внутри линии>`
- Название датчика (задаётся в настройках)
- Текущая температура (число + индикатор)
- Текущая влажность (число + индикатор)
- Статус (цветовая индикация)
- Адреса Modbus
- Имя линии опроса и тип транспорта: COM, UDP RTU или UDP С2000-ПП
- Мини-график за последний час
- Метка актуальности данных каждой плашки: "Последние данные: <дата/время>"
- Источник времени: `temperature.timestamp` датчика (fallback: общий `current.timestamp`)
- «Получено данных сегодня» — счётчик успешных снимков датчика за сутки (из `availability_daily.json`)
- «Ping линии» — строка выводится ТОЛЬКО для датчиков, привязанных к Ethernet-линии (`udp`/`udp_rtu`/`udp_c2000pp`); показывает последний результат ping линии опроса данного датчика (`<мс> мс`, `нет связи` или `—`). Значение берётся по `poll_port_id` датчика из суточного учёта доступности линий. Для датчиков на COM-линии строка ping скрыта

### 5.1.3 Детальный просмотр датчика

- График температуры/влажности
- Масштабирование: час/день/неделя/месяц/год
- Журнал событий датчика
- Настройки границ
- Кнопка квитирования

### 5.1.4 Настройки системы

- Конфигурация опросчика Modbus
- Редактор линий опроса: список линий, добавление COM/UDP, включение/выключение, проверка связи, удаление неиспользуемых линий
- Настройка UDP С2000-ПП: локальный IP/порт, удалённый IP/порт, стартовый SEQ, просмотр последнего SEQ, prefix/channel только как расширенная настройка
- Страница `/settings/poller` в Visualizer должна иметь тот же функциональный объём, что и сервисная страница Modbus Poller: таблица линий, состояние `PollPortManager`, состояние каждого worker, старт/стоп/перезапуск отдельной линии, scan по выбранной линии, последние обмены и ошибки по выбранной линии
- Все изменения линий из `/settings/poller` должны идти через API Modbus Poller или через visualizer-proxy к тем же endpoint, чтобы не появлялись два разных источника правды
- Настройка каждого датчика (добавление, удаление, редактирование)
- Привязка каждого датчика к линии опроса и назначение номера внутри линии
- Настройка архивирования
- Настройка уведомлений

### 5.1.5 Уведомления

- Email при превышении/принижении границ
- Telegram-бот для интерактивного получения данных
- Уведомления в Telegram при превышениях и тревогах
- Периодические отчёты (Email/Telegram) с настраиваемой регулярностью
- Графики за период в отчётах
- Настройка расписания отчётов: ежечасно / ежедневно / еженедельно / ежемесячно

### 5.1.6 Расширенный журнал

- Журнал событий (тревоги, квитирование, изменения конфигурации)
- Журнал температур и влажности с агрегацией по часам/дням/неделям (min/max/avg)
- Журнал превышений границ с длительностью, пиковыми значениями и статусом квитирования
- Фильтрация по датчику, типу события, периоду, статусу

### 5.1.7 План помещения

- Отдельная вкладка «План помещения» в навигации
- Поддержка нескольких планов и подпланов (иерархия)
- Загрузка подложки плана в виде растрового изображения (PNG, JPG, BMP, WebP) или SVG-файла
- SVG-подложка сохраняется как отдельный файл в `visualizer/static/floorplans`, отображается без потери масштаба и не должна исполнять внешние скрипты
- Размещение датчиков на плане методом drag & drop из палитры
- Перетаскивание маркеров датчиков по плану
- Отображение текущих значений (температура, влажность) на маркерах в реальном времени
- Цветовая индикация статуса датчика на маркере (норма / предупреждение / тревога / нет связи)
- Группировка маркеров/плашек на плане: группа имеет название, цвет, список датчиков, состояние `collapsed`, порядок отображения и опциональную рамку на плане
- Редактор группировки на плане: выделение нескольких датчиков, создание группы из выделения, перенос датчиков между группами, разгруппировка
- Удаление датчика с плана (возврат в палитру)
- Создание подпланов (дочерних планов) для детализации отдельных зон
- Удаление плана с каскадным удалением подпланов
- Сохранение конфигурации планов и расположения датчиков в файле `floorplan_config.json`

### 5.1.8 Оформление и темы

- Поддержка двух тем оформления: тёмная (по умолчанию) и светлая
- Переключение темы кнопкой в навигационной панели (мгновенное применение)
- Настройка цветов для каждой темы отдельно через страницу «Настройки → Оформление»
- Настраиваемое название приложения (отображается в навигации и заголовке вкладки браузера, макс. 50 символов, по умолчанию «КВТ Мониторинг»)
- Настраиваемые цвета (для каждой темы):
  - Фон страницы, фон карточек, фон полей ввода
  - Основной и вторичный текст
  - Цвет границ
  - Статусные цвета: норма, охрана/акцент, предупреждение, тревога, нет связи
  - Фон навигации, цвет логотипа
- Сброс цветов темы к значениям по умолчанию
- Предпросмотр статусных цветов на странице настроек
- Все настройки оформления сохраняются в файле `theme_config.json`

### 5.1.9 Дерево датчиков (на мнемосхеме)

- Отдельный блок «Дерево датчиков» на главном экране (мнемосхеме) для логической группировки датчиков по веткам
- Дерево независимо от группировки плашек и от планов помещений; хранится в отдельном файле `mnemo_tree.json`
- Поддержка вложенных веток (подветок); ограничение глубины вложенности — 8 уровней
- Каждая ветка содержит: название, список привязанных датчиков (`sensor_ids`) и список подветок (`children`)
- Один датчик может входить в несколько веток
- В корне каждой ветки отображаются:
  - название ветки;
  - количество датчиков в ветке (с учётом всех подветок);
  - текущий диапазон минимум-максимум температуры по датчикам ветки;
  - текущий диапазон минимум-максимум влажности по датчикам ветки.
- Диапазоны min/max вычисляются по текущим значениям датчиков и обновляются в реальном времени вместе с показаниями
- Ветки сворачиваются/разворачиваются; состояние сворачивания сохраняется между авто-обновлениями страницы
- Листья ветки (датчики) повторяют данные плашки датчика: имя, текущие температуру и влажность, название линии опроса, время последних данных, число полученных данных за сегодня и ping линии (для Ethernet-линий); являются ссылкой на детальный просмотр датчика
- Режим редактирования мнемосхемы: кнопка «Режим редактирования» в шапке главного экрана включает встроенный (inline) редактор дерева под деревом. В режиме редактирования доступны: добавление веток и подветок, переименование, удаление, выбор датчиков в ветку чекбоксами, сохранение и отмена изменений
- Флаг «Показывать плашки вне дерева (все плашки)» в режиме редактирования: управляет отображением общей сетки плашек датчиков. Если выключен — сетка скрывается и на мнемосхеме остаётся только дерево. Изменение применяется сразу (живой предпросмотр) и сохраняется в `mnemo_tree.json` (поле `show_flat_cards`, по умолчанию `true`)
- При сохранении выполняется санация: пустые/повторяющиеся идентификаторы веток переназначаются, дубликаты и некорректные `sensor_ids` отбрасываются

## 5.2 Структура страниц

```
/                       - Главный экран (мнемосхема)
/floorplan              - План помещения (планы, подпланы, размещение датчиков)
/sensor/{id}            - Детальный просмотр датчика
/settings               - Настройки системы (общие)
/settings/poller        - Настройки Modbus опросчика
/settings/opcua         - Настройки OPC UA сервера и состава публикуемых датчиков
/settings/sensors       - Настройки датчиков (добавить/удалить/изменить)
/settings/archive       - Настройки архивирования
/settings/notifications - Настройки уведомлений и Telegram-бота
/settings/reports       - Настройки журналов учёта: журналы-отчёты, операторы (ФИО), календарь праздников
/settings/appearance    - Настройки оформления (темы, цвета, название)
/settings/system        - Системные настройки и версионность
/settings/config-transfer - Импорт/экспорт полного конфигурационного архива
/events                 - Журнал событий
/journal/temperatures   - Журнал температур и влажности (диапазоны по дням/неделям)
/journal/violations     - Журнал превышений границ
/logbook                - Журнал учёта (складская отчётность): суточные значения + ежедневное подтверждение
/logbook/{id}/print     - Печатный/PDF лист журнала учёта за период
/export                 - Экспорт данных
```

## 5.3 Цветовая индикация статусов

Цвета статусов настраиваются отдельно для каждой темы через `theme_config.json` и страницу «Настройки → Оформление».

**Значения по умолчанию (тёмная тема):**

| Статус | Цвет | Hex |
|--------|------|-----|
| normal | Зелёный | #4CAF50 |
| guarded | Синий | #2196F3 |
| warning_* | Жёлтый/Оранжевый | #FF9800 |
| alarm | Красный | #F44336 |
| no_connection | Серый | #9E9E9E |

**Значения по умолчанию (светлая тема):**

| Статус | Цвет | Hex |
|--------|------|-----|
| normal | Зелёный | #16a34a |
| guarded | Синий | #2563eb |
| warning_* | Оранжевый | #ea580c |
| alarm | Красный | #dc2626 |
| no_connection | Серый | #9ca3af |

## 5.8 Суточный учёт доступности (availability_daily.json)

Файл `data/availability_daily.json` ведёт учёт доступности линий опроса и датчиков в пределах текущих суток (при смене даты счётчики сбрасываются). Используется счётчиком «Получено данных сегодня» и строкой «Ping линии» в карточках датчиков, привязанных к Ethernet-линиям.

```json
{
  "date": "2026-06-17",
  "updated_at": "2026-06-17T12:22:42",
  "sensors": {
    "1": {
      "id": 1,
      "name": "Датчик 1",
      "poll_port_id": "udp_mq7w4t4v",
      "samples_today": 198,
      "received_today": 159,
      "failed_today": 39,
      "availability_percent": 80.3
    }
  },
  "ports": {
    "udp_mq7w4t4v": {
      "id": "udp_mq7w4t4v",
      "name": "UDP-C2000PP-new",
      "transport": "udp_c2000pp",
      "remote_host": "192.168.66.100",
      "remote_port": 40005,
      "network_checks": 120,
      "network_ok_checks": 118,
      "network_availability_percent": 98.3,
      "last_network_available": true,
      "last_ping_ms": 3.0,
      "network_history": [
        { "timestamp": "2026-06-17T12:22:42", "available": true, "ping_ms": 3.0 }
      ]
    }
  }
}
```

| Поле | Описание |
|------|----------|
| sensors[].received_today | Количество успешных снимков датчика за сутки (значение «Получено данных сегодня») |
| sensors[].availability_percent | Доля успешных снимков от общего числа за сутки |
| ports[].network_availability_percent | Процент успешных сетевых проверок (ping) линии за сутки |
| ports[].last_ping_ms | Последний измеренный ping линии, мс (для значения «Ping линии» в карточке датчика) |
| ports[].network_history | История точек доступности линии (доступна через API, на мнемосхеме отдельной плашкой не отображается) |

> Ping выполняется только для Ethernet-линий (`udp`/`udp_rtu`/`udp_c2000pp`). Для COM-линий сетевая проверка не производится, и строка «Ping линии» в карточке датчика скрывается.

## 5.11 Журнал учёта (складская отчётность)

**Назначение.** Электронный аналог бумажного журнала учёта температуры и влажности, который традиционно ведётся на складах: по выбранным датчикам за **каждые сутки** фиксируются минимум, максимум и среднее значения температуры и влажности, а ответственный сотрудник **ежедневно подтверждает («расписывается»)**, что ознакомился с показаниями и они соответствуют наблюдаемым. Подсистема обеспечивает прослеживаемость и пригодна для предъявления при аудите.

### 5.11.1 Функциональные требования

- Поддержка нескольких настраиваемых журналов-отчётов; каждый журнал охватывает свой набор датчиков (выбор вручную или из веток дерева мнемосхемы) и имеет тип (`warehouse` — складской, требует ежедневного подтверждения; `general` — без подтверждения).
- Суточные значения (min/max/avg температуры и влажности, число превышений) вычисляются из архива (Archive Manager); день идентифицируется датой `YYYY-MM-DD`.
- Ежедневное подтверждение оператором: выбор ФИО из управляемого списка операторов (без пароля); фиксируются ФИО, дата и время подтверждения и **снимок суточных значений** на момент подписи.
- Выходные (суббота/воскресенье) и праздники определяются календарём; за нерабочие дни возможно **пакетное подтверждение** одним действием при подписи ближайшего рабочего дня.
- Подтверждённые записи **неизменяемы**: последующее изменение архивных данных не меняет уже подписанную запись (хранится снимок).
- Подсветка неподтверждённых рабочих дней (просрочек) и отображение статуса заполнения журнала.
- Печатный / PDF лист журнала за период (месяц), пригодный для бумажного аудита, с колонкой подписи (ФИО, дата подтверждения).
- Админ-страница управления журналами, списком операторов и календарём праздников.

### 5.11.2 Конфигурация журналов (reports_config.json)

```json
{
  "reports": [
    {
      "id": "rep1",
      "name": "Складской журнал — Бокс 1",
      "type": "warehouse",
      "sensor_ids": [13, 20, 21],
      "branch_ids": [],
      "columns": ["t_min", "t_max", "t_avg", "h_min", "h_max", "h_avg", "violations"],
      "require_daily_signoff": true,
      "active": true
    }
  ],
  "updated_at": "2026-06-24T10:00:00"
}
```

| Поле | Описание |
|------|----------|
| reports[].id | Идентификатор журнала (генерируется/нормализуется на сервере: `rep1`, `rep2`, …) |
| reports[].name | Название журнала (до 120 символов) |
| reports[].type | `warehouse` — складской (требует ежедневного подтверждения) либо `general` — справочный |
| reports[].sensor_ids | ID датчиков из `system_config.json`, входящих в журнал |
| reports[].branch_ids | Альтернативно — ID веток дерева мнемосхемы (датчики берутся из веток) |
| reports[].columns | Состав отображаемых суточных колонок |
| reports[].require_daily_signoff | Требуется ли ежедневное подтверждение оператором |
| reports[].active | Активен ли журнал |

### 5.11.3 Операторы (operators.json)

```json
{
  "operators": [
    {"id": "op1", "last_name": "Иванов", "first_name": "Иван", "middle_name": "Иванович", "position": "кладовщик", "active": true}
  ],
  "updated_at": "2026-06-24T10:00:00"
}
```

| Поле | Описание |
|------|----------|
| operators[].id | Идентификатор оператора |
| operators[].last_name / first_name / middle_name | ФИО заполняющего |
| operators[].position | Должность (для печатного листа) |
| operators[].active | Доступен ли для выбора при подтверждении |

### 5.11.4 Календарь рабочих дней (holidays.json)

```json
{
  "weekends": [5, 6],
  "holidays": [
    {"date": "2026-01-01", "name": "Новый год"},
    {"date": "2026-05-09", "name": "День Победы"}
  ],
  "rf_calendar_years": [2026],
  "updated_at": "2026-06-24T10:00:00"
}
```

| Поле | Описание |
|------|----------|
| weekends | Дни недели, считающиеся выходными (по `datetime.weekday()`: 5 = суббота, 6 = воскресенье) |
| holidays[].date / name | Праздничные (нерабочие) даты — вводятся вручную |
| rf_calendar_years | Годы, для которых выполнена предзагрузка производственного календаря РФ |

- Рабочий день: день недели не входит в `weekends` И дата не входит в `holidays`.
- Предзагрузка производственного календаря РФ (праздники/переносы) выполняется по годам и сохраняется в `holidays` (с возможностью ручной правки); при отсутствии данных используются только Сб/Вс.

### 5.11.5 Суточные значения (источник данных)

Суточные строки (по дню и датчику: `t_min/t_max/t_avg`, `h_min/h_max/h_avg`, число превышений) берутся из файловой «вьюхи» `archive_daily.json`, формируемой Archive Manager; при её отсутствии — агрегируются из `archive.json` по дню (ключ `YYYY-MM-DD`). Сетевой прокси к Archive Manager не используется.

### 5.11.6 Подтверждение и хранилище подписей (logbook_signoffs.json)

```json
{
  "signoffs": [
    {
      "report_id": "rep1",
      "date": "2026-06-24",
      "operator_id": "op1",
      "operator_name": "Иванов И. И.",
      "signed_at": "2026-06-24T18:05:00",
      "comment": "",
      "non_working": false,
      "batch_covered": [],
      "snapshot": {
        "13": {"t_min": 3.1, "t_max": 5.8, "t_avg": 4.4, "h_min": 40.2, "h_max": 55.1, "h_avg": 47.0, "violations": 0}
      }
    }
  ]
}
```

| Поле | Описание |
|------|----------|
| report_id / date | Журнал и сутки, за которые поставлено подтверждение |
| operator_id / operator_name | Кто подтвердил (ID и отображаемое ФИО) |
| signed_at | Дата и время подтверждения |
| comment | Необязательный комментарий оператора |
| non_working | Признак того, что день нерабочий (подтверждён пакетно) |
| batch_covered | Список нерабочих дат, подтверждённых вместе с этой записью |
| snapshot | Снимок суточных значений по датчикам на момент подписи (для неизменяемости/аудита) |

- Пара `(report_id, date)` подтверждается один раз; повторное подтверждение отклоняется.
- Запись хранит снимок значений — последующее изменение архива не изменяет подписанную строку.

### 5.11.7 Пакетное подтверждение за выходные и праздники

При подтверждении рабочего дня оператор может одним действием подтвердить **все предшествующие непрерывные нерабочие дни** (выходные и праздники). Для каждого такого дня создаётся запись с `non_working = true` и тем же оператором; перечень покрытых дат фиксируется в `batch_covered` записи рабочего дня.

### 5.11.8 Печатный / PDF лист

Журнал за месяц формируется в печатном виде (A4, печать средствами браузера → PDF): шапка (название журнала, период, объект), строки по дням с суточными значениями по каждому датчику и колонка подписи (ФИО, дата подтверждения). Нерабочие дни и просроченные (неподтверждённые) рабочие дни визуально выделяются.
