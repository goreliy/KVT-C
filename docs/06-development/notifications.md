# Уведомления

Настройки находятся в **Настройки → Уведомления** (`/settings/notifications`).
Почта и Telegram выключены по умолчанию. Служба уведомлений автоматически
запускается в процессе `archiver.app`, в том числе при запуске через `run_kvt.py`.
Настройки перечитываются каждые две секунды, рестарт после сохранения не нужен.
После обновления исходников уже работающий архиватор нужно перезапустить.

## Почта

- **Без шифрования** — обычное SMTP-соединение, обычно порт 25.
- **STARTTLS** — соединение обязательно переключается на TLS до авторизации и
  передачи письма, обычно порт 587. Отказ STARTTLS прекращает отправку.
- **TLS сразу** — защищённое соединение с первого байта, обычно порт 465.

Порт задаётся вручную по требованиям почтового сервера. Пустой пользователь
отключает SMTP AUTH. Можно задать пароль приложения, отправителя, несколько
получателей, таймаут, доверенный CA и клиентский сертификат с ключом.
TLS использует минимум TLS 1.2. Проверка цепочки сертификатов и имени сервера
включена по умолчанию; её можно явно отключить для выбранного подключения.
Относительные пути сертификатов считаются от корня данных КВТ (`KVT_HOME`
или каталог приложения). Ключ клиентского сертификата должен загружаться
без интерактивного запроса пароля.

Кнопка **Сохранить и отправить тестовое письмо** сначала сохраняет настройки,
потом отправляет письмо всем указанным получателям. Включение автоматических
уведомлений для теста не требуется. Ответ «принято сервером» означает принятие
SMTP-сервером, а не подтверждение получения человеком.

## События и очередь

Обрабатываются свежие показания из `data/current.json` датчиков, включённых
и поставленных под охрану в `system_config.json`. Пороговые значения берутся
из `temp_limits` / `hum_limits`; поддерживается также вложенный `limits`.
Температура и влажность отслеживаются отдельно. Сообщение создаётся при
переходе в предупреждение/тревогу или между их уровнями и направлениями.
Повтор одного состояния на каждом цикле опроса не создаёт новых сообщений.
Возврат в норму включается отдельно. Показания старше 120 секунд и значения
без связи игнорируются. Уведомления о потере связи пока не реализованы.

Учитываются глобальные `on_alarm`, `on_warning`, `on_recovery`, флаги датчика
`notifications.email_on_alarm` и аналогичные, а также переопределения
`notifications.json.per_sensor` по строковому ID датчика.

### Получатели датчиков и групп

На странице уведомлений можно создать именованные группы и выбрать для них
датчики. У каждого датчика и группы почта и Telegram настраиваются независимо:
«Наследовать», «Свои адреса» или «Не отправлять».

Приоритет адресов для каждого канала:

1. Собственные адреса датчика или его явное отключение.
2. Объединённые адреса всех групп этого датчика, задающих получателей.
   Совпадающий адрес в нескольких группах получает одно сообщение о событии.
   Группа с режимом «Не отправлять» не добавляет адресов; другие группы могут
   продолжать отправку. Если все назначающие группы отключены, получателей нет.
3. Общие получатели, если датчик и его группы наследуют настройки.

SMTP, TLS и учётные данные остаются общими для почтового канала. Адреса
переопределяют только получателей. Общий список может быть пустым — тогда
уведомления получат только отдельно назначенные адресаты. Ежедневная сводка
использует общий список. Смена назначения действует на будущие события и
отменяет ожидающие сообщения адресатам, исключённым из назначения.

Перед тестовой отправкой можно выбрать датчик: используется тот же алгоритм
адресации, что при настоящем событии. Обычный тест использует общий список.

В JSON отсутствие `email_recipients` / `telegram_chat_ids` означает наследование,
пустой список означает отключение. Например:

```json
{
  "per_sensor": {
    "1": {"email_recipients": ["owner@example.ru"]},
    "2": {"telegram_chat_ids": []}
  },
  "groups": [
    {"id": "warehouse", "name": "Склад", "sensor_ids": [1, 2, 3],
     "email_recipients": ["warehouse@example.ru"], "telegram_chat_ids": ["-100123"]}
  ]
}
```

Редактор сохраняет адреса вместе с остальными настройками. Параметр
`replace_routing: true` в POST заменяет целиком `per_sensor` и `groups`, что
позволяет удалять назначения и группы. Без него `per_sensor` обновляется
частично. Старые флаги уведомлений датчиков сохраняются при редактировании адресов.

Состояния и очередь сохраняются в `data/notifications.db`. Каждому получателю
соответствует отдельная запись. Ошибка вызывает до трёх попыток с задержками;
после третьей запись остаётся в состоянии `failed`. Выключенный канал и удалённый
получатель отменяют ожидающие сообщения при обработке очереди. Уже созданные
сообщения не отменяются при восстановлении датчика и содержат время события.
Статистика и последняя ошибка доступны на странице и в
`data/notifications_status.json`. После сбоя между принятием сообщения сервером
и записью результата возможна повторная доставка; SMTP Message-ID сохраняется
при повторе. Размер базы автоматически не ограничивается.

Ежедневная почтовая сводка — текстовый снимок последних показаний с временем
снимка, один раз в сутки после указанного времени на компьютере КВТ. Это не
архивный отчёт за сутки. Пропущенные дни не восстанавливаются.

Telegram отправляет текст через HTTPS Bot API. Нужно задать токен и Chat IDs.
Графики, Telegram-команды и расписания отчётов Telegram пока не реализованы;
старые поля этих функций сохранены для совместимости.

## Учётные данные и API

Пароль SMTP и токен Telegram сохраняются отдельно в
`data/config/notification_secrets.key`, не возвращаются через API/HTML и
не включаются в ZIP-экспорт настроек. Файл содержит секреты в открытом виде:
его защищают права доступа ОС, отдельного шифрования на диске нет.
Старые секреты из `notifications.json` переносятся при следующем сохранении.
После переноса настроек на другой компьютер секреты нужно ввести заново.

- `GET /api/notifications` — настройки и признаки наличия секретов.
- `POST /api/notifications` — частичное обновление с проверкой значений.
  Пустой пароль/токен сохраняет прежний; `email.clear_password` /
  `telegram.clear_token` удаляют секрет явно.
- `POST /api/notifications/test`, `{"channel":"email"}` или
  `{"channel":"telegram"}` — тест по сохранённым настройкам.
  Необязательный `sensor_id` (целое число) выбирает адресатов датчика.
- `GET /api/notifications/status` — состояние службы, очередь и ошибки.

## Проверка

Из корня проекта: `python -B -m unittest discover -s tests`.
Тесты используют временные файлы и SMTP-сервер на loopback с временным
сертификатом. Проверяются три режима подключения, доверие сертификату,
имя сервера, отсутствие отката STARTTLS, миграция секретов, API, очереди
и переходы состояний, приоритет адресов датчика и групп, удаление назначений
и отмена ожидающих сообщений после смены адреса. Настоящему почтовому серверу
сообщения не отправляются.

Браузерная проверка редактора: `node tests/test_notification_routing.cjs`.
Нужен Playwright и установленный Microsoft Edge. Если Playwright находится
в отдельном каталоге, задайте `KVT_PLAYWRIGHT_MODULE` равным пути его пакета.
Тест проверяет создание/удаление групп, выбор датчиков, адреса, наследование,
отключение канала, поиск и сохранение старых флагов. Внешняя сеть не используется.
